# 🚀 Gemini CLI Update Report: The Guardrails of Autonomy

**Date:** November 26, 2025
**Topic:** Autonomous Agents, Safety Layers, and Human-in-the-Loop Controls

## 1. Feature Summary
This release introduces **`--guardrails`**, a new configuration layer for the Gemini CLI’s autonomous agent mode. While the Gemini CLI has been able to execute complex multi-step tasks, this update provides a granular permission system. It allows developers to define "safe zones" for file system access, network requests, and command execution, ensuring that the AI can act autonomously within boundaries but requires human approval for high-risk actions.

## 2. Background & Context
**Why was this change made?**
As discussed in the referenced blog post, the transition from "Chat" to "Agent" brings significant risk. Users want the AI to refactor code or deploy infrastructure, but they are rightfully terrified of an agent hallucinating a destructive command (like `rm -rf /` or dropping a production database).

**The Problem:**
Previously, using the `--auto` flag was a binary choice: either the AI had full control to execute commands, or the user had to approve *every single step*. This created friction:
*   **Too permissive:** High risk of unintended side effects.
*   **Too restrictive:** The user becomes a "human micro-manager," defeating the purpose of autonomy.

**The Solution:**
Based on the implementation context, this feature introduces a tiered risk assessment engine. The CLI now parses intended commands *before* execution and compares them against a user-defined policy (the "Guardrails"). This creates a "trust but verify" workflow described as "Bounded Autonomy."

## 3. How-To Guide

### Setting up a Guardrails Policy
You can now control the agent's autonomy using a `.gemini-guardrails.yaml` file in your project root or via CLI flags.

**1. Create a policy file:**
```yaml
# .gemini-guardrails.yaml
version: 1.0
protection_level: strict

# Whitelist: The agent can run these without asking
allowed_commands:
  - "ls -*"
  - "cat *"
  - "git status"
  - "npm test"

# Blacklist: The agent is forbidden from running these
blocked_commands:
  - "rm -rf /"
  - "aws * delete-*"

# Intervention: The agent must ask for permission for these
require_approval:
  - "git push"
  - "npm publish"
  - "writing to files outside ./src"
```

**2. Running the Agent with Guardrails:**
Run a complex refactoring task. The CLI will read the local policy file automatically.

```bash
gemini agent "Refactor the authentication logic in auth.ts to use the new provider" --guardrails
```

**3. The Experience:**
*   *Scenario A (Safe):* The agent runs `cat src/auth.ts`. **Result:** Executes silently.
*   *Scenario B (Risk):* The agent tries to write to the file. **Result:**
    ```text
    ⚠️  GUARDRAIL ALERT: Agent is attempting to overwrite 'src/auth.ts'.
    Policy: 'Write operations require approval'
    > Allow this specific action? [y/N/always]
    ```

## 4. Walkthrough / Technical Deep Dive

The "Guardrails" feature works via a new middleware layer in the CLI's execution loop.

1.  **Intent Parsing:** When the LLM generates a tool call (e.g., executing a shell command), the CLI intercepts the request before it reaches the OS shell.
2.  **AST Analysis:** The command string is parsed into an Abstract Syntax Tree (AST) (using a lightweight shell parser). This allows the system to distinguish between `rm file.txt` (delete file) and `echo "rm file.txt"` (print text), avoiding false positives.
3.  **Policy Evaluation:**
    *   The parsed command is matched against the regex patterns and rules defined in `.gemini-guardrails.yaml`.
    *   It checks file system paths (e.g., is the agent trying to read `/etc/passwd` or just `./README.md`?).
4.  **Heuristic Risk Scoring:** If no specific rule matches, the CLI assigns a risk score based on the verb (e.g., `curl` is medium risk, `rm` is high risk, `ls` is low risk).
5.  **Execution Branch:**
    *   **Pass:** Command executes, output is fed back to the LLM.
    *   **Block:** The LLM receives an error: `PermissionDeniedByPolicy`. The LLM can then try a different approach or ask the user for help.
    *   **Review:** The CLI pauses the spinner and prompts the user via `stdin`.
