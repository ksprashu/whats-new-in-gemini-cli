# 🚀 What's New: Completely Customize Your Gemini CLI

## 1. Feature Summary
The Gemini CLI has introduced a robust **Configuration and Profiling System**. Users can now persist their preferred settings—such as default models, temperature, output formats, and system instructions—into a local configuration file. Additionally, the CLI now supports **"Workflows" (Profiles)**, allowing you to instantly switch between different contexts (e.g., specific settings for "Coding" vs. "Creative Writing") without typing out repetitive flags every time.

## 2. Background & Context
**The Problem:**
Previously, the Gemini CLI was stateless. If a developer wanted to use `gemini-1.5-pro` with a high temperature for brainstorming, they had to manually append flags to every single command:
`gemini prompt "Idea for a story..." --model gemini-1.5-pro --temperature 0.9`

**The "Why" (from the Community):**
*   **Repetition Fatigue:** Developers noted in issue discussions that 90% of their commands used the same non-default flags, leading to frustration.
*   **Context Switching:** Users often switch between distinct tasks. One moment they are debugging code (requiring low temperature, specific system prompts), and the next they are writing documentation (requiring higher creativity). Doing this via command flags was error-prone.

**The Solution:**
This update shifts the CLI from a strictly flag-based tool to a configuration-aware tool. By introducing a YAML-based config file, we allow the CLI to adapt to the user's environment, not the other way around.

## 3. How-To Guide

### Step 1: Initialize the Config
Run the new initialization command to generate a default configuration file in your home directory (usually `~/.config/gemini/config.yaml`).

```bash
gemini config init
```

### Step 2: Edit Your Global Defaults
Open the generated file. You can now set your global defaults.

```yaml
# ~/.config/gemini/config.yaml
defaults:
  model: "gemini-1.5-pro"
  temperature: 0.7
  output: "markdown"
  safety_settings: "block_none"
```

Now, running `gemini prompt "Hello"` automatically uses `gemini-1.5-pro`.

### Step 3: Define Workflows (Profiles)
This is the power user feature. You can define named workflows in the config file:

```yaml
workflows:
  coder:
    model: "gemini-1.5-pro"
    temperature: 0.1
    system_instruction: "You are an expert Golang engineer. Be concise."
  
  writer:
    model: "gemini-ultra"
    temperature: 0.9
    system_instruction: "You are a creative copywriter. Use flowery language."
```

### Step 4: Use a Workflow
Invoke a specific profile using the `--workflow` (or `-w`) flag:

```bash
gemini prompt "Fix this function" -w coder
gemini prompt "Write a tagline" -w writer
```

## 4. Walkthrough / Technical Deep Dive

### Configuration Precedence Logic
To ensure flexibility, the Gemini CLI now utilizes a specific "hierarchy of truth" when resolving settings. It resolves parameters in the following order (highest priority first):

1.  **Command Line Flags:** Explicit flags always win.
    *   *Example:* `gemini prompt "Hi" --temperature 0.5` overrides any config setting.
2.  **Environment Variables:** `GEMINI_MODEL=gemini-nano` overrides the config file.
3.  **Active Workflow:** Settings defined in the selected `-w` profile.
4.  **Global Defaults:** Settings in the `defaults` section of `config.yaml`.
5.  **Hardcoded Fallbacks:** If nothing is set, the CLI falls back to internal defaults (e.g., `gemini-pro`, temp 0.7).

### Architecture
Under the hood, this update introduces a singleton Configuration Manager that loads on CLI startup.
*   **File Parsing:** We utilize a YAML parser to read the user's config.
*   **Validation:** The CLI creates a schema validation step before execution. If your config file contains an invalid parameter (e.g., `temperature: 5.0`), the CLI will throw a validation error immediately rather than sending a bad request to the API.
