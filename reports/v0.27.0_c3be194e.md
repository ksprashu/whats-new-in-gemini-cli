## The Headline
The Gemini CLI is receiving a massive internal upgrade that users will feel, even if they can't see it. The development team has overhauled the engine that handles tool execution, moving from a legacy linear model to a modern, **Event-Driven Architecture**. Think of this as replacing a standard transmission with a dual-clutch automatic; the shifting between thinking, calling tools, and processing results is now smoother, faster, and significantly more responsive. While the interface remains familiar, the interaction loop is now powered by a high-performance scheduler designed to handle complex, multi-step agentic tasks with ease.

## Quick Start / How to Try It Out
To test the new event-driven scheduler, users must opt-in via the configuration file, as this feature currently runs alongside the legacy system via a feature toggle.

*   **Prerequisites / Flags**: Enable the scheduler in your configuration file (typically located at `.gemini/config.ts` or similar based on setup). Look for the experimental flags section.
    ```typescript
    // Inside .gemini/config.ts
    export default {
      experimental: {
        useEventDrivenScheduler: true // Toggle this flag
      }
    };
    ```
*   **Commands**: Once enabled, use Gemini as normal. The difference is best felt during complex tool use.
    ```bash
    gemini prompt "Analyze the src/ directory, list all Todo items, and summarize the technical debt."
    ```

## Use Cases (Why you need this)
*   **Complex Multi-Step Chains:** When asking Gemini to perform tasks that require chaining multiple tools (e.g., "Search the web, then read this file, then write a test"), the new scheduler manages the hand-offs more efficiently.
*   **UI Responsiveness:** The event-driven nature decouples the execution logic from the UI thread, meaning the terminal UI remains responsive (less "freezing") while Gemini is crunching heavy data or waiting on API responses.
*   **Debugging & Observability:** For developers building on top of the CLI, the event bus architecture provides clearer insight into exactly when a tool is requested, executed, and confirmed.

## What to Expect (Things to Look Out For)
*   **Parity is the Goal:** Ideally, the output should look identical to the stable version. If tool outputs appear out of order or confirmation prompts behave strangely, this is a regression.
*   **Latency:** Users should notice a decrease in perceived latency between steps, specifically in how quickly the CLI updates status messages during tool execution.

## Technical Deep Dive (Admin)
This update represents a fundamental architectural shift in how the Gemini CLI orchestrates operations, managed via Pull Request #17078. The implementation introduces a **Facade Pattern** via a new hook, `useToolScheduler.ts`. This hook acts as a traffic controller, dynamically routing execution requests to either the legacy `useReactToolScheduler` or the new `useToolExecutionScheduler` based on the configuration flag.

Key architectural components include:
*   **MessageBus Integration:** The new scheduler utilizes a `MessageBus` for communication, decoupling the scheduling logic from the UI rendering components.
*   **Core Scheduler:** Logic has been moved to a dedicated `Scheduler` entity within the core package, reducing logic bloat in the React front-end layer.
*   **Adapter Pattern:** To ensure the existing UI components didn't require a complete rewrite, the team implemented an adapter within `useToolExecutionScheduler`. This adapter injects MessageBus-proxying `onConfirm` callbacks into Core objects, ensuring that legacy UI components can still "talk" to the new event-driven backend without knowing it exists.
*   **Unified Type Safety:** The PR unifies tool tracking types, enforcing a consistent data contract regardless of which scheduler is active.

## Background & Context (Admin)
The move to an event-driven architecture addresses the limitations of the legacy scheduler, which was becoming a bottleneck for "Agentic" workflows. As Gemini's capabilities expanded from simple Q&A to complex multi-tool autonomous actions, the linear, tightly coupled nature of the old scheduler made state management difficult and UI updates sluggish.

Issue #14306 tracks the broader migration effort. The legacy system struggled with concurrency and clean separation of concerns. By adopting an event-driven model, the engineering team prepares the CLI for future features that may require parallel tool execution or background processing, aligning the CLI with modern asynchronous application standards.
