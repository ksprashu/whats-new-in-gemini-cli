# 🚀 What's New: The "Clean Sweep" Scheduler Architecture

**PR:** [#16895](https://github.com/google-gemini/gemini-cli/pull/16895) | **Author:** @abhipatel12 | **Status:** Merged (Foundational)

## 1. Feature Summary
We have introduced a significant architectural overhaul to the Gemini CLI’s core execution engine, known internally as the **"Clean Sweep"** architecture. This update refactors the central Scheduler component, separating monolithic execution logic into distinct, specialized modules.

While this change is currently a "no-op" (meaning the old scheduler is still active while this code is integrated), it lays the critical groundwork for a more reliable, type-safe, and testable agent loop. It prepares the CLI for complex future operational flows by decoupling orchestration from business logic.

## 2. Background & Context
**The Problem:**
As the Gemini CLI capabilities grew, the original Scheduler component became responsible for too many concerns simultaneously: managing the execution queue, enforcing security policies, and handling user confirmations (TUI/IDE interactions). This tight coupling introduced risks of:
*   **Race Conditions:** Multiple processes trying to update the state simultaneously.
*   **Testing Difficulty:** Hard to unit test orchestration logic when it is intertwined with UI logic.
*   **Maintenance Overhead:** Implementing new permission scopes or execution modes became increasingly complex.

**The Solution:**
PR #16895 addresses these issues by enforcing a strict **Separation of Concerns**. By isolating responsibilities, we ensure that the orchestrator only "orchestrates," while specialized modules handle decisions and permissions. This improves the overall robustness of the system and eliminates a class of concurrency bugs.

## 3. How-To Guide
**For End Users:**
Because this is a foundational architectural change, **no action is required on your part.** You can continue using the Gemini CLI as normal. Once the "Clean Sweep" scheduler is fully activated in upcoming releases, you may notice improved stability during long-running agent tasks and faster tool execution.

**For Contributors/Developers:**
If you are contributing to the Gemini CLI codebase, you will notice a new file structure in the core module. When adding new execution logic, you must now interact with the specific module responsible for that logic rather than the main Scheduler file.

To explore the new structure locally:
1.  Navigate to the `core/scheduler` directory.
2.  Review `policy.ts` for permission logic.
3.  Review `confirmation.ts` for UI interaction logic.

## 4. Walkthrough / Technical Deep Dive
The "Clean Sweep" architecture breaks the scheduler down into three primary pillars:

### A. The Pure Orchestrator (`Scheduler.ts`)
The `Scheduler.ts` file has been stripped of business logic. It is now a **pure, event-driven orchestrator**.
*   **Responsibility:** Queue management and execution lifecycle.
*   **Mechanism:** It listens for events and delegates decision-making to other modules. It does not decide *if* a tool can run, only *when* it runs within the queue.

### B. The Policy Module (`policy.ts`)
A dedicated security and logic gatekeeper.
*   **Responsibility:** Centralizes all permission checks.
*   **Key Checks:**
    *   **YOLO Mode:** Checks if auto-approval is enabled.
    *   **Allowed Tools:** Verifies if the requested tool is on the allowlist.
    *   **MCP Scopes:** Validates Model Context Protocol permissions.

### C. The Confirmation Module (`confirmation.ts`)
The bridge between the agent and the human.
*   **Responsibility:** Handles the interactive loop (TUI or IDE).
*   **Features:** Allows users to confirm, reject, or modify tool calls before they are executed. By isolating this, we ensure the UI thread does not block the internal state machine of the scheduler unnecessarily.

### Improved Testability
Extensive integration tests were added to `scheduler.test.ts`, `policy.test.ts`, and `confirmation.test.ts`. This ensures that scenarios like **batch auto-approval**, **cancellation flows**, and **executor status handling** are verified via automated tests rather than manual QA.
