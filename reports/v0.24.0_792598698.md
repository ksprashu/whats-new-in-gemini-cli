# Gemini CLI Release Report: Architecture Hardening & Built-in Skills

**Release Date:** October 2023
**Contributors:** @abhipatel12, @NTaylorMullen

## 1. Feature Summary
This release marks a pivotal moment in the maturity of the Gemini CLI architecture. We are moving from flexible experimental structures to robust, enforced patterns.

*   **Mandatory MessageBus (Phase 3):** The core communication layer—the `MessageBus`—is now a required dependency for all tools. This completes "Phase 3" of our internal migration, eliminating optionality to ensure consistent inter-tool communication and policy enforcement.
*   **Built-in Skills:** The CLI now supports shipping with "batteries included." We have introduced a mechanism to bundle essential skills directly within the core package, removing the need for users to manually install foundational capabilities.
*   **Subagent Routing:** Enhanced model routing logic now effectively utilizes subagents, allowing the CLI to dispatch specific tasks to specialized agentic flows.

## 2. Background & Context

### Why Make `MessageBus` Mandatory? (PR #15776)
Previously, the `MessageBus` was an optional parameter in many tool constructors. While this offered flexibility during early development, it led to fragmented communication logic. Some tools could "talk" to the system, while others operated in isolation.

By enforcing mandatory injection, we are solving two problems:
1.  **Consistency:** Every tool is now guaranteed to have access to the communication layer. We removed conditional checks (e.g., `messageBus ?? this.messageBus`), which simplifies the codebase.
2.  **Future-Proofing:** A centralized bus allows us to enforce global policies (like security redaction or audit logging) on every message passed between tools.

### Why Built-in Skills? (PR #16300)
As the CLI ecosystem grows, requiring users to download every single basic skill individually creates friction. This change introduces a `packages/core/src/skills/builtin` directory. The goal is to streamline the distribution of essential functionalities so the CLI is useful immediately after installation.

## 3. How-To Guide

### For CLI Extension Developers: Updating Tool Constructors
If you are maintaining a custom tool or extension for the Gemini CLI, this is a **breaking change**. You must update how you instantiate tools.

**Previous Implementation (Deprecated):**
```typescript
// Old way: MessageBus was optional
const myTool = new CustomTool(config); 
```

**New Implementation (Required):**
You must now inject the `MessageBus` instance explicitly.

```typescript
// New way: MessageBus is mandatory
const messageBus = new MessageBus();
const myTool = new CustomTool(config, messageBus);
```

### For Users: Accessing Built-in Skills
There is no action required for end-users. Built-in skills are now automatically discovered and loaded. You can verify they are active by running the help command, which will now list these core capabilities alongside your custom-installed skills.

```bash
gemini --help
# You will see built-in skills listed automatically
```

## 4. Walkthrough / Technical Deep Dive

### The Hard Migration to MessageBus (PR #15776)
The engineering team refactored the `ToolRegistry` and `Config` classes.
1.  **Registry Update:** The `ToolRegistry` constructor now strictly demands a `MessageBus`.
2.  **Cleanup:** The `Config` class’s `createToolRegistry` method was updated to align with this, and the deprecated `setMessageBus` method was removed.
3.  **Instantiation:** All call sites within `core` and `cli` packages were updated to pass the bus instance.

### The Skill Discovery Mechanism (PR #16300)
The `SkillManager` has been upgraded to support a dual-loading strategy:
1.  **Directory Scanning:** It looks into `packages/core/src/skills/builtin`.
2.  **Build Process:** The `copy_files.js` script was modified to ensure this directory is physically included in the final build artifact.
3.  **Identification:** When loaded, these skills are tagged with an `isBuiltin` flag. This flag is exposed to the UI and logic layers, allowing us to prevent users from accidentally deleting core skills or to visually distinguish them in the interface.

### Subagent Model Routing
*Based on the changelog and Issue #16289:* The routing logic has been decoupled. Instead of a single monolithic prompt handler, the system can now identify intent and route the request to a "subagent"—a specialized model configuration optimized for specific tasks (e.g., a "Git Commit Agent" vs. a "Code Refactoring Agent").

## 5. Next Steps for Demos

When showcasing this release to the community or internal stakeholders, I recommend the following three demos:

1.  **"Zero-Config" Start:**
    *   *Scenario:* Install a fresh version of the CLI.
    *   *Action:* Immediately run a complex command that relies on a Built-in Skill.
    *   *Talking Point:* Highlight that no plugin installation was required; the CLI is smarter out of the box.

2.  **The "Subagent" Hand-off:**
    *   *Scenario:* Ask the CLI a multi-part question (e.g., "Review this PR and then summarize the changes").
    *   *Action:* Show the verbose logs where the router identifies the intent and dispatches it to the specific subagent.
    *   *Talking Point:* Demonstrate improved accuracy and efficiency via specialized routing.

3.  **Dev Mode: The Safety Net:**
    *   *Scenario:* Attempt to initialize a tool *without* a MessageBus in a live coding session.
    *   *Action:* Show the immediate compile-time (or runtime) error.
    *   *Talking Point:* Explain how this "strict mode" prevents silent failures and ensures all tools can communicate with the system.
