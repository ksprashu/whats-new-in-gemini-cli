# What’s New: Event-Driven Tool Execution Scheduler

**PR:** [#17078](https://github.com/google-gemini/gemini-cli/pull/17078) | **Contributor:** [@abhipatel12](https://github.com/abhipatel12) | **Status:** Merged

## 1. Feature Summary
The Gemini CLI has undergone a significant architectural upgrade with the introduction of an **Event-Driven Tool Execution Scheduler**.

Previously relying on a legacy execution model, the CLI now utilizes a modern `MessageBus` system for handling tool interactions. This change acts as a foundational performance boost, decoupling the User Interface (UI) from the heavy lifting of tool execution. The result is a CLI that feels snappier, handles complex tool chains more efficiently, and offers a more robust foundation for future extensions—all while maintaining full backward compatibility with the existing UI.

## 2. Background & Context
**Why was this change made?**
As the Gemini CLI capabilities expanded, the "legacy" scheduler—responsible for orchestrating how the AI invokes external tools and reports results—began to show its age. Tightly coupled execution logic often makes it difficult to implement asynchronous flows, advanced error handling, or parallel tool execution without blocking the user interface.

**The Solution**
This update (PR #17078) represents a major milestone in migrating the CLI’s execution engine. Instead of a "rip-and-replace" strategy which carries high regression risk, the team implemented a **Facade Architecture**. This allows the system to support both the legacy scheduler and the new event-driven scheduler simultaneously.

By moving to an event-driven model, the CLI aligns with standard modern software patterns where components communicate via signals (events) rather than direct dependencies. This paves the way for a more reactive and maintainable codebase.

## 3. How-To Guide
For most end-users, this change is transparent—you get the performance benefits automatically without changing your workflow. However, for developers contributing to the CLI or running local builds, understanding the toggle mechanism is key.

### For End Users
Simply update to the latest version of the Gemini CLI. The new scheduler is designed to work seamlessly with all your existing prompts and scripts.

```bash
gemini update
# Resume using standard commands
gemini prompt "Summarize this PR and run the unit tests"
```

### For Contributors/Debuggers
The architecture now includes a "Facade Hook" that determines which scheduler to use. While primarily internal, if you are developing extensions or debugging tool behavior, note that the CLI logic now branches based on configuration flags.

If you are inspecting the codebase, look for `useToolScheduler.ts`. This is the traffic cop:
*   **Legacy Path:** Routes to `useReactToolScheduler`
*   **Modern Path:** Routes to `useToolExecutionScheduler` (The new event-driven implementation)

## 4. Walkthrough / Technical Deep Dive
The engineering behind this update relies on three specific design patterns: **Facade**, **MessageBus**, and **Adapter**.

### The Facade Hook (`useToolScheduler.ts`)
The entry point for tool execution is now a Facade. It checks a configuration flag to decide which engine to spin up. This ensures that if any issues arise with the new system, the CLI can fall back to the legacy system instantly without a code rollback.

### The Core: Event-Driven Architecture (`useToolExecutionScheduler.ts`)
In the new path, the CLI uses a **MessageBus**.
1.  **Trigger:** When the LLM decides to use a tool, it emits an event.
2.  **Transport:** The MessageBus captures this event and routes it to the specific handler in the Core Scheduler.
3.  **Execution:** The tool runs asynchronously.
4.  **Response:** Results are published back to the bus.

### The Adapter Pattern
One of the biggest challenges in this PR was ensuring the existing React UI (which expects specific data formats from the old scheduler) didn't break.
*   **The Solution:** An **Adapter Layer** was introduced within `useToolExecutionScheduler`.
*   **Function:** It injects proxies into the Core objects. When the Core fires a MessageBus event, the Adapter translates that into the state updates and "onConfirm" callbacks that the existing UI components already understand.
*   **Benefit:** We get a modern engine under the hood without having to rewrite the entire front-end dashboard.

### Type Safety
The PR also unified tool tracking types. There is now a consistent data contract used by both the legacy and modern implementations, reducing technical debt and making TypeSciprt analysis stricter and safer.
