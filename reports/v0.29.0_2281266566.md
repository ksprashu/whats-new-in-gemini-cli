# 🚀 What's New in Gemini CLI: Admin Controls for MCP

**Version Update:** Reflected in PR #18311  
**Contributor:** @skeshive

## 1. Feature Summary
We have introduced a critical enterprise security feature: **Admin Allowlisting for Model Context Protocol (MCP) Servers**.

Administrators can now enforce governance over the Gemini CLI by defining a strict list of approved MCP server configurations. This prevents the CLI from connecting to unauthorized, untrusted, or insecure external context providers, ensuring that AI-assisted workflows remain compliant with organizational security standards.

## 2. Background & Context
**The Problem:**
As the Model Context Protocol (MCP) ecosystem grows, developers can connect the Gemini CLI to various external tools and databases. While powerful, this presents a "shadow IT" risk where developers might inadvertently connect to unvetted third-party servers or insecure internal endpoints, potentially exposing sensitive data or ingesting malicious context.

**The Solution:**
Addressed in **PR #18311** and tracked via **Issue #1178**, this update shifts control from the end-user to the administrator. By implementing an explicit allowlist (whitelist), the CLI moves from a "default allow" to a "default deny" posture regarding MCP connections. This ensures that the Gemini CLI only interacts with approved integration points.

## 3. How-To Guide
*Note: The following configuration keys are illustrative of the standard implementation patterns for this feature. Please verify exact file paths in your specific distribution.*

### Step 1: Locate the Admin Configuration
Administrators should modify the global/system-level configuration file for the Gemini CLI (typically located in `/etc/gemini/config.json` on Linux/macOS or `%PROGRAMDATA%\Gemini\config.json` on Windows).

### Step 2: Define the Allowlist
Add the `mcp_servers` or `allowlist` block. Only servers defined here will be accessible to users.

```json
{
  "adminPolicy": {
    "enforceMcpAllowlist": true,
    "allowedMcpServers": [
      {
        "name": "internal-docs-db",
        "url": "https://mcp.internal.acme.corp/docs"
      },
      {
        "name": "jira-integration",
        "command": "npx",
        "args": ["-y", "@acme/jira-mcp-server"]
      }
    ]
  }
}
```

### Step 3: User Experience
When a developer tries to add or connect to a server:

**Scenario A: Allowed Server**
```bash
$ gemini mcp connect https://mcp.internal.acme.corp/docs
> ✅ Successfully connected to 'internal-docs-db'.
```

**Scenario B: Blocked Server**
```bash
$ gemini mcp connect https://sketchy-plugin.com/api
> ❌ Error: Connection blocked by administrative policy.
> The server 'https://sketchy-plugin.com/api' is not in the allowlist.
> Please contact your IT administrator.
```

## 4. Walkthrough / Technical Deep Dive
The implementation in PR #18311 likely introduces a middleware check during the MCP connection initialization phase.

1.  **Config Resolution:** When the CLI starts up, it loads configuration in a specific order of precedence:
    *   Default Settings
    *   System/Admin Config (Where this feature lives)
    *   User Config (`~/.gemini/config`)
2.  **Policy Check:** Before establishing a WebSocket or Stdio connection to an MCP server, the CLI checks if `enforceMcpAllowlist` is active.
3.  **Validation Logic:**
    *   The CLI compares the requested connection (URL or Command) against the `allowedMcpServers` array.
    *   The matching logic typically requires an exact string match or a regex pattern match (depending on strictness) to prevent bypassing via query parameters.
4.  **Hard Stop:** If the validation fails, the process throws a security exception immediately, preventing any data handshake between the LLM and the unauthorized source.
