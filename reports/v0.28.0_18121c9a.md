## The Headline
The Gemini CLI team has rolled out a significant refinement to the authentication workflow, prioritizing user agency and transparency. Gone are the days when the system might abruptly launch a browser window the moment an OAuth flow was triggered. With this update, the CLI now explicitly asks for permission before initiating the handshake with the browser. Alongside this UX improvement, the developer experience gets a boost with smarter bug reporting that automatically captures authentication contexts, streamlining the troubleshooting loop between users and maintainers.

## Quick Start / How to Try It Out
These features are part of the core authentication and diagnostics modules and do not require experimental flags.

*   **Prerequisites**: Ensure you are running the latest version of the Gemini CLI.
*   **To see the Consent Flow**:
    Simply trigger a login sequence or run a command requiring fresh authentication.
    ```bash
    gemini login
    ```
    *Expect to see a new prompt in your terminal asking for confirmation before the browser opens.*

*   **To see the Bug Report Update**:
    Run the bug reporting command.
    ```bash
    gemini bug
    ```
    *Inspect the generated report draft; you will notice your active authentication method is now pre-populated in the system details.*

## Use Cases (Why you need this)
*   **Security-Conscious Workflows**: Developers working in shared screen environments or recording demos no longer have to worry about the CLI unexpectedly popping open browser windows containing sensitive login tokens without a "ready" signal.
*   **Headless/SSH Environments**: The new flow handles terminal-only environments better. If a user is SSH'd into a remote machine, the CLI attempts a `readline` prompt or fails gracefully with a clear error, rather than silently trying to launch a GUI browser that doesn't exist.
*   **Rapid Support**: When things go wrong, users often forget to mention *how* they are logged in (OAuth vs. API Key). The automated inclusion of auth methods in bug reports eliminates this first round of "back-and-forth" with support.

## What to Expect (Things to Look Out For)
*   **The "Extra" Click**: Long-time users might be surprised by the pause in the login flow. You now must hit `Y` (or Enter) to proceed to the browser.
*   **CI/CD Failures**: If you are running the CLI in a strictly non-interactive environment (CI pipelines) without pre-configured tokens, the system will now throw a `FatalAuthenticationError` rather than hanging or timing out while waiting for a browser that can't launch. This is a "fail-fast" improvement but may require script adjustments.

## Technical Deep Dive (Admin)
The architecture behind the authentication flow has been refactored to introduce an event-driven consent barrier (PR #17699).

*   **Event-Driven Architecture**: The core change introduces a `ConsentRequest` event. In a GUI context, the application listens for this event to present a dialog.
*   **Terminal Fallback**: For the CLI, the `AppContainer` and `DialogManager` now utilize a `readline` interface to capture standard input (`stdin`) for confirmation.
*   **Error Handling**: The refactor explicitly handles "Headless" states. If the environment is non-interactive and not a TTY (Teletype), the system throws a `FatalAuthenticationError`. This prevents the "zombie process" scenario where the CLI waits for a browser interaction that is impossible to perform.
*   **Diagnostics Injection**: Regarding PR #17569, the `bugCommand.test.ts` and associated logic were updated to query the active `AuthStrategy` instance. This string identifier is then injected into the Markdown template generated by `/bug`, ensuring the auth context travels with the issue report.

## Background & Context (Admin)
This update addresses two specific friction points in the developer ecosystem:
1.  **UX Jarring**: Previous iterations of the CLI could feel intrusive, taking focus away from the terminal to the browser without warning. This aligns with broader industry best practices for CLI tools (like the AWS CLI or GitHub CLI) where actions with side effects (opening browsers) usually require confirmation.
2.  **Support Velocity**: Maintainers noted that bug reports frequently lacked context regarding authentication methods. Since debugging an OAuth failure is vastly different from debugging a Service Account key failure, PR #17569 was introduced to enforce context collection programmatically.
