## 4. Walkthrough / Technical Deep Dive

### Under the Hood: The Retry Mechanism
In **PR #160**, we refactored the HTTP client layer. Previously, we used a standard `fetch` implementation. We have wrapped this in a custom `ResilientClient` class.

Here is the logic flow implemented:
1.  **Interceptor:** The client intercepts the response before passing it back to the main thread.
2.  **Status Check:** If the status is `429` (Too Many Requests) or `503` (Service Unavailable), it triggers the Retry Loop.
3.  **Jittered Backoff:** To prevent "thundering herd" problems, we use exponential backoff with random jitter:
    $$ \text{sleep} = \min(\text{cap}, \text{base} \cdot 2^{\text{attempt}}) + \text{random\_jitter} $$
4.  **Max Retries:** Defaults to 3 attempts before raising a fatal error.

This ensures that the CLI is robust enough for production scripting without requiring users to write their own bash `while` loops to handle retries.
