# 🚀 What’s New: Dynamic Telemetry Configuration via Environment Variables

**PR:** [#9113](https://github.com/google-gemini/gemini-cli/pull/9113) | **Author:** @jerop

## 1. Feature Summary
The Gemini CLI now supports configuring telemetry settings directly through environment variables. This update moves beyond static configuration files, allowing developers to manage telemetry behavior dynamically using `GEMINI_TELEMETRY_*` variables.

In addition, a new configuration option, `useCollector`, has been introduced to support advanced OpenTelemetry Protocol (OTLP) collector workflows.

**Key Highlights:**
*   **Environment-First Configuration:** Telemetry settings can be injected via the environment.
*   **Strict Precedence:** Environment variables now strictly override `settings.json` and CLI flags.
*   **OTLP Support:** New support for connecting to custom collectors.

## 2. Background & Context
**The Problem:**
Previously, configuring telemetry required modifying the `settings.json` file or passing specific CLI flags. While sufficient for local development, this approach created friction in containerized environments, CI/CD pipelines, and automated deployments where modifying static files is cumbersome or anti-pattern.

**The Solution:**
Based on discussions in Issue #9084 and implemented in PR #9113, the Gemini CLI now adheres to "Twelve-Factor App" principles by allowing configuration via the environment. This ensures that:
1.  **DevOps Compatibility:** Settings can be injected into Docker containers or Kubernetes pods at runtime.
2.  **Security & Compliance:** Telemetry can be globally disabled or redirected in sensitive environments without touching the codebase or local config files.

## 3. How-To Guide

### Basic Configuration
You can now control the telemetry state without opening a JSON file. The system listens for variables prefixed with `GEMINI_TELEMETRY_`.

**Enable/Disable Telemetry globally:**
```bash
# Linux/macOS
export GEMINI_TELEMETRY_ENABLED=false

# Windows (PowerShell)
$env:GEMINI_TELEMETRY_ENABLED="false"
```

### Advanced: Using the OTLP Collector
A new boolean setting, `useCollector`, allows you to route data through an OpenTelemetry collector.

```bash
# Configure Gemini CLI to use a custom collector
export GEMINI_TELEMETRY_USE_COLLECTOR=true
export GEMINI_TELEMETRY_COLLECTOR_ENDPOINT="http://localhost:4317"
```

### Verifying Precedence
This feature relies on specific hierarchy rules. If you have `settings.json` configured one way, but the environment variable configured another way, the **Environment Variable wins**.

**Example:**
*   `settings.json`: `{"telemetry": {"enabled": false}}`
*   Environment: `export GEMINI_TELEMETRY_ENABLED=true`
*   **Result:** Telemetry will be **ENABLED**.

## 4. Walkthrough / Technical Deep Dive

The core logic of this update resides in how the CLI initializes its configuration loader. The PR introduces a prioritization logic that evaluates settings in the following order (from highest priority to lowest):

1.  **Environment Variables (`GEMINI_TELEMETRY_*`)**: These are checked first. If present, they bypass all other configurations.
2.  **`settings.json`**: If no environment variables are detected, the CLI falls back to the persistent user configuration file.
3.  **CLI Flags / Defaults**: If neither of the above defines the setting, system defaults are applied.

**The `useCollector` Implementation:**
The `useCollector` boolean is a new addition to the internal telemetry struct. When set to `true`, the CLI alters its initialization routine to instantiate an OTLP exporter rather than the default direct-to-cloud exporter. This allows enterprise users to aggregate Gemini CLI metrics alongside their existing application infrastructure traces.

**Quality Assurance:**
To ensure this hierarchy creates no regressions, a new test suite was added in the PR. These tests programmatically set conflicting environment variables and JSON values, asserting that the environment variable always dictates the final runtime state.
