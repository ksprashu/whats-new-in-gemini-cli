# 🚀 What’s New: The "Rock-Solid" Input Engine Update

**Release:** Gemini CLI Update (PR #7118)
**Contributor:** @deepankarsharma

---

## 1. Feature Summary
In this release, the Gemini CLI has undergone a significant overhaul of its **keyboard input handling engine**. We have replaced the previous input logic with a robust, "peel-and-continue" parser.

**The result?** A drastically smoother typing experience. Whether you are using standard arrow keys, special navigation keys (Home, End), or complex modifier combinations (Ctrl/Alt/Shift), the CLI now interprets them consistently across a much wider variety of terminal emulators (including modern ones like Kitty and Alacritty).

---

## 2. Background & Context
**The Problem:**
Terminal input is notoriously difficult to standardize. Different terminal emulators send different escape sequences for the same physical keys. Furthermore, when using the CLI over SSH or in resource-constrained environments, input streams can arrive **fragmented** (split across multiple data packets) or **batched** (multiple keystrokes arriving instantly in one packet).

Previously (as alluded to in Issue #6227), users likely experienced friction where:
*   Arrow keys resulted in garbage text (e.g., `^[[A`) instead of moving the cursor.
*   Rapid typing caused the input parser to "choke" or miss characters.
*   Modern terminals using the Kitty keyboard protocol were not fully supported.

**The Solution:**
PR #7118 introduces a fundamental architectural shift. Instead of relying on simple matching, the new parser is designed to handle the messy reality of raw terminal streams, ensuring that user intent is captured accurately regardless of how the terminal delivers the data.

## 3. How-To Guide
Because this is an infrastructure improvement, there is no new configuration flag to enable. It works out of the box. However, here is how you can verify and utilize the improvements:

### Step 1: Update
Ensure you are running the latest version of the Gemini CLI containing the merge from PR #7118.

### Step 2: Test Navigation Keys
Open the CLI and type a long prompt. Try using the following keys to navigate the text:
*   **Home / End**: Should jump strictly to the start or end of the line.
*   **Ctrl + Arrow Keys**: Should jump word-by-word (depending on your specific terminal mapping).
*   **Delete / Backspace**: Should behave consistently without lag.

### Step 3: Test Complex Environments
If you previously had issues using the Gemini CLI inside specific emulators (like **Kitty**, **WezTerm**, or the **VS Code integrated terminal**), launch the CLI there. You should notice that special keys that previously failed are now recognized instantly.

## 4. Walkthrough / Technical Deep Dive
For the developers and curious users, here is what changed under the hood in the `parseKittyPrefix` and input logic.

### The "Peel-and-Continue" Parser
The star of this update is the move to a **"peel-and-continue" parsing strategy**.
*   **Old Way:** The parser often expected a specific sequence in a specific timeframe. If a sequence was split between buffers, it might fail.
*   **New Way:** The parser looks at the incoming stream of bytes. It identifies a valid escape sequence (e.g., an arrow key), "peels" it off the front of the stream, processes it, and immediately continues to the next byte. This allows it to handle **batched inputs** (e.g., a user pasting text or typing incredibly fast) without dropping data.

### Robust Sequence Support
The parser now natively understands a broader dictionary of ANSI escape sequences:
1.  **Parameterized Keys:** Sequences that include arguments defining which modifiers (Shift/Ctrl) are held down.
2.  **Tilde-Coded Keys:** Legacy sequences used by older terminals (e.g., `~` terminated sequences for PageUp/PageDown).
3.  **Legacy Arrows:** Fallback support for basic cursor movement sequences.

### Handling Fragmentation
By buffering the input stream more intelligently, the CLI can now handle **fragmented streams**. If the CLI receives the first half of an escape code in one cycle and the second half in the next, the parser waits to resolve the full key rather than printing garbage characters to the screen.
