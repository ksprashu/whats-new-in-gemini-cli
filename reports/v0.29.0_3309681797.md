# What’s New in Gemini CLI: Experimental Extension Registry UI

## 1. Feature Summary
We are introducing a new **Extension Exploration UI** to the Gemini CLI. This feature provides a visual interface for users to discover, explore, and manage CLI extensions, moving beyond command-line-only management.

Because this is a significant change to the user interface, it has been released as an **Experimental** feature. It is disabled by default to ensure stability for existing workflows, but can be unlocked via a new configuration setting (`extensionRegistry`) for those eager to test the new discovery experience.

## 2. Background & Context
**Why was this change made?**
As the Gemini CLI ecosystem grows, managing extensions purely through text commands can become cumbersome. Users need an easier way to browse available plugins and tools.

**The Solution**
PR #18686 introduces the foundational plumbing for an "Extension Registry Explore UI." However, the team opted for a "safe rollout" strategy.
*   **Granular Control:** By wrapping this feature in a configuration flag, we allow power users and early adopters to test the UI without affecting the stability of the core CLI for the general user base.
*   **Schema Validation:** The change isn't just a hidden switch; it is formally defined in the CLI's setting schema, ensuring that users get proper validation and descriptions when editing their configuration.

## 3. How-To Guide
To enable the new Extension Registry UI, you will need to modify your local configuration file.

**Prerequisites:**
*   Ensure you have updated to the latest version of Gemini CLI containing this change.

**Steps:**

1.  **Open your Settings:**
    Locate your `settings.json` file (or open the configuration via your IDE if the CLI is integrated there).

2.  **Add the Configuration Flag:**
    Add the `extensionRegistry` property to the root of your settings object and set it to `true`.

    ```json
    {
      "extensionRegistry": true
      // ... other existing settings
    }
    ```

3.  **Restart the CLI:**
    *Note:* As indicated in the PR, this setting **requires a restart** to take effect. Please kill any running instances of the CLI or restart your terminal/IDE session.

4.  **Verify:**
    Once restarted, access the extensions menu. You should now see the new "Explore" or "Registry" UI elements enabled.

## 4. Walkthrough / Technical Deep Dive
For developers interested in how we manage experimental features, here is a look under the hood at PR #18686.

**The Configuration Schema**
The core logic relies on strict typing and schema validation. We updated `packages/cli/src/config/settingsSchema.ts` to include the new definition. This ensures that the CLI knows exactly how to treat this flag before the UI even loads.

```typescript
// packages/cli/src/config/settingsSchema.ts (Conceptual Snippet)
extensionRegistry: {
  type: 'boolean',
  default: false,
  description: 'Enables the experimental Extension Registry Explore UI.',
  scope: 'window', // Requires window/process reload
  experimental: true
}
```

**Schema Propagation**
This TypeScript definition is then compiled into `schemas/settings.schema.json`. This JSON file allows editors (like VS Code) and the CLI itself to provide:
1.  **Hover Tooltips:** Explaining that the feature is "Experimental."
2.  **Validation:** Preventing you from passing a string or integer where a boolean is required.
3.  **Default States:** ensuring the feature remains off (`false`) unless explicitly invoked.

When the CLI boots up, it reads this config. If `extensionRegistry` checks out as `true`, the CLI injects the new UI components into the view layer; otherwise, those components remain unloaded to save resources.
