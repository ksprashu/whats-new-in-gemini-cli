# 🚀 What's New: Introducing Conductor for Gemini CLI

## 1. Feature Summary
**Conductor** is a new extension for the Gemini CLI that introduces a formal **"Planning Phase"** to the AI coding workflow. Termed "Context-Driven Development" (CDD), Conductor prevents the LLM from jumping immediately to code generation. Instead, it acts as an architect, analyzing your request and your codebase to generate a detailed implementation plan (an artifact).

This extension ensures the LLM has strict guardrails and a comprehensive understanding of the task before a single line of code is written. It is the embodiment of the engineering mantra: *"Measure twice, cut once."*

## 2. Background & Context
### The Problem: The "Context Window" Trap
Developers often face a specific friction point when using AI CLIs:
1.  **Premature Coding:** When a user asks for a complex feature, LLMs often attempt to solve it in one shot.
2.  **Hallucination via Isolation:** Without a full plan, the AI might generate code that conflicts with existing architectural patterns or misses dependencies.
3.  **The "Undo" Loop:** Users spend more time debugging the AI's first draft than it would have taken to write the code themselves.

### The Solution: Context-Driven Development
Based on the blog post and changelog, Conductor was built to decouple **Reasoning** from **Implementation**. By forcing a planning step, Conductor solves the "blank page" problem. It pulls in extra context (file definitions, documentation, related classes) to build a robust mental model of the project *before* attempting implementation.

## 3. How-To Guide

### Prerequisites
*   Gemini CLI (Latest Version)
*   A valid API Key configured

### Step 1: Installation
Install the extension directly via the Gemini CLI package manager:

```bash
gemini extensions install https://github.com/gemini-cli-extensions/conductor
```

### Step 2: The Planning Workflow
Instead of asking Gemini to "write code," you now ask Conductor to "create a plan."

**Example Command:**
```bash
gemini conductor plan "Refactor the user authentication flow to support OAuth2 providers"
```

### Step 3: Reviewing the Artifact
Conductor will not change your source code yet. Instead, it generates a Markdown artifact (e.g., `PLAN.md` or a temporary buffer output).

*   **Review:** Read the plan. It will list the files to be modified, the new data structures proposed, and the step-by-step logic.
*   **Iterate:** If the plan looks wrong, you can chat with Conductor to refine it: *"Make sure to include GitHub and Google as providers."*

### Step 4: Execution
Once the plan is approved, Conductor passes the structured context to the Gemini coder agent:

```bash
gemini conductor apply
```

## 4. Walkthrough / Technical Deep Dive

Under the hood, Conductor operates as a multi-step agentic workflow:

1.  **Intent Analysis:** Conductor parses the user prompt to identify the scope (e.g., is this a bug fix, a refactor, or a new feature?).
2.  **Context Retrieval (The "Pull"):** Unlike a standard CLI chat, Conductor actively scans your directory. It likely uses a lightweight AST (Abstract Syntax Tree) analysis or file-header reading to identify relevant files that will be impacted by the change.
3.  **Artifact Generation:** It synthesizes this data into a structured prompt for the underlying Gemini model. The output is a **Specification Artifact**. This artifact serves as the "Guardrails."
4.  **Guided Generation:** When `apply` is triggered, the Gemini CLI uses the Artifact as the "System Prompt" or "Context." This drastically reduces hallucination because the model is no longer guessing the architecture—it is following the blueprint it just wrote.
