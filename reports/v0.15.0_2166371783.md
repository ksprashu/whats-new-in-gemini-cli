# What’s New: Enhanced Security Control for Extensions

**Release Date:** *[Insert Date]*
**Pull Request:** [#12838](https://github.com/google-gemini/gemini-cli/pull/12838)
**Contributor:** @kevinjwang1

## 1. Feature Summary
The Gemini CLI has introduced a new security configuration, `security.blockGithubExtensions`, designed to harden the developer environment. This feature allows users and organization administrators to explicitly disable the installation and loading of extensions sourced directly from Git repositories or GitHub releases. This change ensures that only trusted, local, or registry-verified extensions are utilized, significantly reducing the surface area for executing arbitrary third-party code.

## 2. Background & Context
**The Challenge:**
In modern CLI ecosystems, extensions are a powerful way to expand functionality. However, allowing extensions to be pulled directly from remote Git repositories or unverified GitHub releases introduces potential security risks. These "supply chain" risks occur when a user unknowingly installs code from a repository that hasn't undergone strict vetting, or when a previously safe repository is compromised.

**The Solution:**
Addressing discussion in **Issue #12557**, this update shifts control back to the user. By default, developers often prioritize convenience, but enterprise environments and security-conscious users require strict governance over what code runs on their machines.

This PR introduces a "circuit breaker" for external code. It ensures that if a user (or their organization's policy) decides that remote GitHub extensions are too risky, they can enforce a blockade at the application level.

## 3. How-To Guide

To utilize this new security feature, you will need to modify your Gemini CLI configuration.

### Enabling the Block
You can enable this setting via your configuration file (typically `config.json` or `.gemini/config`) or, depending on your CLI version, via the command line.

**Option A: Configuration File**
Add the `security` object and the boolean flag to your config file:

```json
{
  "security": {
    "blockGithubExtensions": true
  }
}
```

**Option B: CLI Command (If supported)**
```bash
gemini config set security.blockGithubExtensions true
```

### What Happens When Enabled?

**Scenario 1: Attempting a new installation**
If you attempt to install an extension from a GitHub URL while this setting is active:
```bash
gemini extension install https://github.com/user/unverified-extension.git
```
**Result:** The CLI will immediately abort the operation and return an error message indicating that installation from remote sources is blocked by security policy.

**Scenario 2: Existing Extensions**
If you previously installed an extension from GitHub and *then* enabled this setting:
**Result:** Upon the next run of the Gemini CLI, the Extension Manager will skip loading these specific extensions. Your local extensions will continue to function, but remote-sourced ones will be effectively disabled.

## 4. Walkthrough / Technical Deep Dive
The implementation of PR #12838 touches the core `ExtensionManager` logic within the CLI. Here is how it functions under the hood:

1.  **Configuration Parsing:** Upon initialization, the CLI reads the `security.blockGithubExtensions` boolean.
2.  **Installation Guard:**
    *   When the `install` command is invoked, the argument parser checks the source of the extension.
    *   If the source matches patterns associated with Git repositories (e.g., ends in `.git`, contains `github.com`) AND the security flag is `true`, a validation exception is thrown before any network requests are made.
3.  **Loader Filtering (Runtime Protection):**
    *   The CLI maintains metadata about installed extensions, including their `installationSource`.
    *   During the startup sequence, the `ExtensionManager` iterates through installed plugins.
    *   A new conditional check verifies if the plugin's origin is remote/GitHub.
    *   If the security flag is enabled, these specific plugins are filtered out of the execution context, preventing their code from being loaded into memory.

This dual-layer approach (Block on Install + Block on Load) ensures that the system is secure even if the configuration is applied *after* risky extensions have already been installed.

## 5. Next Steps for Demos
To effectively showcase this feature in a video or live demo, I recommend the following flow:

1.  **The "Before" State:**
    *   Show `security.blockGithubExtensions` set to `false` (default).
    *   Successfully install a harmless "Hello World" extension from a public GitHub repo.

2.  **The Lockdown:**
    *   Open the config file and change the setting to `true`.
3.  **The "After" State (Load Prevention):**
    *   Run the Gemini CLI again. Show that the previously installed extension is no longer listed in `gemini extension list` or fails to trigger its command, proving it was not loaded.
4.  **The "After" State (Install Prevention):**
    *   Attempt to install a *new* extension from GitHub.
    *   Highlight the error message explicitly stating the action was blocked by security policy.
5.  **The Safe Alternative:**
    *   Demonstrate that a local extension (installed from a local file path) still works, proving that you haven't broken the tool, only secured the perimeter.
