# 🚀 What’s New: Direct-to-Cloud Telemetry for Gemini CLI

**Release Date:** *[Insert Date]*

## 1. Feature Summary
The Gemini CLI has significantly streamlined its observability story. With the introduction of **Direct to Google Cloud Telemetry**, developers can now send traces and metrics directly from their local CLI environment to Google Cloud Trace and Monitoring without requiring complex intermediate infrastructure.

This change removes the friction of setting up local collectors, allowing for instant visibility into your GenAI application's performance and latency.

## 2. Background & Context
**The Friction of OpenTelemetry**
Previously, visualizing what the Gemini CLI was doing "under the hood" (latency per step, tool usage, API calls) required a standard OpenTelemetry (OTEL) setup. This often meant:
1.  Running a local OTEL Collector (usually via Docker).
2.  Configuring the CLI to export via OTLP to that local port.
3.  Configuring the Collector to forward that data to a backend.

**The Solution**
Based on PR #8541 and community feedback (Issues #6792, #7204), the team recognized that this setup was too heavy for many developers who just wanted quick insights.

**The Trade-off**
To solve this, we have bundled the official Google Cloud Trace and Metric exporters directly into the `gemini.js` bundle.
*   **Impact:** This resulted in a **+3.67 MB (+26.96%)** increase in the binary size (bringing the total to 17.3 MB).
*   **Benefit:** The "batteries-included" experience. The heavy lifting of gRPC and Protobuf handling is now native to the CLI, eliminating the need for external sidecars.

## 3. How-To Guide

Here is how to start visualizing your Gemini CLI interactions in Google Cloud.

### Prerequisites
*   A Google Cloud Project with the **Cloud Trace API** enabled.
*   Google Cloud SDK installed locally.

### Step 1: Authenticate
The CLI relies on Application Default Credentials (ADC) to send telemetry securely.

```bash
gcloud auth application-default login
```

### Step 2: Configure the CLI
You can now configure the CLI to point directly to your project.

```bash
# Example configuration (Syntax may vary based on exact release flags)
export GOOGLE_CLOUD_PROJECT="your-project-id"
export GEMINI_TELEMETRY_MODE="google-cloud"
```

### Step 3: Run a Command
Run your standard Gemini commands. The latency is slightly higher on the *very first* request as the exporter initializes, but subsequent requests remain fast.

```bash
gemini prompt "Explain the architecture of a neural network"
```

### Step 4: View in Console
Navigate to the Google Cloud Console -> **Trace** -> **Trace Explorer**. You will see a waterfall view of your CLI command, breaking down the time spent on local processing vs. API latency.

## 4. Walkthrough / Technical Deep Dive

### Under the Hood
This update modifies the initialization logic of the CLI's telemetry service.

1.  **Detection:** When the CLI starts, it checks the telemetry configuration. If "Google Cloud" is selected, it bypasses the standard OTLP (OpenTelemetry Protocol) HTTP/gRPC exporter logic.
2.  **Instantiation:** It initializes `NodeJS` exporters provided by the `@google-cloud/opentelemetry-cloud-trace-exporter` and `@google-cloud/opentelemetry-cloud-monitoring-exporter` packages.
3.  **Bundling:** As noted in the PR analysis, the `gemini.js` bundle grew by nearly 4MB. This is because the Google Cloud exporters require specific gRPC native bindings and protobuf definitions to communicate efficiently with Google's backend APIs.
4.  **Transmission:** As the CLI executes, spans are batched locally. Upon command completion (or strictly defined flush intervals), these batches are pushed directly to the Google Cloud Trace API endpoints.

### Architecture Comparison

*   **Before:** `CLI` -> *OTLP (HTTP)* -> `Local Collector (Docker)` -> *gRPC* -> `Google Cloud`
*   **After:** `CLI` -> *gRPC (Authenticated)* -> `Google Cloud`
