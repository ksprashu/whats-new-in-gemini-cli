# Gemini CLI: What’s New 
### Streamlined Approvals via Keybindings

**PR:** [#6665](https://github.com/google-gemini/gemini-cli/pull/6665)  
**Author:** @bulkypanda  

---

## 1. Feature Summary
The latest update to the Gemini CLI introduces a significant quality-of-life improvement for power users. **Keybinding Triggered Approvals** allow developers to simultaneously approve a pending confirmation dialog *and* switch operation modes (YOLO or Auto-Edit) with a single keystroke. 

When you use shortcuts like `Shift+Y` (YOLO mode) or `Shift+Tab` (Auto-Edit mode) while a confirmation prompt is active, the CLI will now interpret this as a "Yes" to the current prompt, immediately executing the pending action while entering the requested mode.

## 2. Background & Context
**The Problem:**
Previously, utilizing the Gemini CLI involved a slight friction point during "mid-stream" decision making. 

Imagine the CLI suggests a shell command and waits for your confirmation (`[y/n]`). If you looked at the command and decided, "Yes, run this, and actually, just run everything else automatically from now on," you had to perform a "double-tap":
1. Press `y` to approve the current command.
2. Wait for the state to return.
3. Press `Shift+Y` to toggle YOLO mode.

**The Solution:**
This change, implemented by @bulkypanda, recognizes that switching to a more autonomous mode (like YOLO) implies consent for the immediate action. By coupling the mode switch with an implicit approval, the CLI reduces keystrokes and keeps developers in the "flow state." It aligns user intent with tool behavior—if you trust the tool enough to go "YOLO," you certainly trust the command currently on the screen.

## 3. How-To Guide
This feature works out of the box with existing shortcuts. Here is how to utilize it in your workflow:

### Scenario A: The "Trust Fall" (YOLO Mode)
1.  Ask Gemini CLI to perform a multi-step task (e.g., "Refactor the authentication middleware and update the tests").
2.  The CLI proposes the first shell command: `npm install passport`.
3.  **Prompt:** `Run this command? [y/N]`
4.  **Action:** Instead of pressing `y`, press **`Shift+Y`**.
5.  **Result:** The CLI accepts "Yes" for `npm install`, runs it, and immediately switches to **YOLO mode**, executing all subsequent commands without asking for further permission.

### Scenario B: fast-Forwarding Edits (Auto-Edit Mode)
1.  The CLI proposes a change to `server.js`.
2.  **Prompt:** `Apply these changes? [y/N]`
3.  **Action:** Press **`Shift+Tab`**.
4.  **Result:** The current file changes are applied immediately, and the CLI enters **Auto-Edit mode**, applying future file edits automatically.

## 4. Walkthrough / Technical Deep Dive
Under the hood, this feature modifies the input handling logic within the CLI's read-eval-print loop (REPL).

Previously, keypress listeners for global shortcuts (like `Shift+Y`) were likely treated as strictly modal toggles that did not interact with the specific `inquirer` or `prompt` instance currently awaiting user input.

With PR #6665, the event handler has been updated to check the state of the active prompt:
1.  **Event Interception:** When `Shift+Y` or `Shift+Tab` is detected, the listener checks if there is an unresolved `Promise` related to a user confirmation dialog.
2.  **Promise Resolution:** If a dialog is active, the system programmatically resolves the confirmation promise with `true` (equivalent to the user typing `y` and hitting Enter).
3.  **State Mutation:** Simultaneously, the global state manager updates the `mode` flag (toggling `yolo` or `auto_edit` to `true`).
4.  **Execution:** The CLI proceeds to execute the pending command/edit and continues the loop in the new mode.

This ensures there are no race conditions where the mode switches but the prompt remains "stuck" waiting for input.
