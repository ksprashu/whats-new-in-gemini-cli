# 🛡️ Gemini CLI Update: Secure-by-Default Trust & Context-Aware Policies

**Release Focus:** Security Hardening & Policy Engine Flexibility
**Related PRs:** [#15943](https://github.com/google-gemini/gemini-cli/pull/15943), [#15977](https://github.com/google-gemini/gemini-cli/pull/15977)

## 1. Feature Summary
This release marks a significant milestone in the security posture of the Gemini CLI. We have shifted the **Folder Trust** mechanism to a "secure-by-default" model, meaning the CLI now assumes all unknown folders are untrusted until explicitly verified by the user.

Simultaneously, we have upgraded the **Policy Engine**. Administrators and users can now define specific **Modes** (such as `autoEdit` or `yolo`) within their policy files. This allows for granular allowlisting of shell commands that are active only during specific workflows, effectively bridging the gap between flexibility and safety.

## 2. Background & Context

### The Problem: Implicit Trust & Rigid Policies
Previously, when the `folderTrust` feature was enabled, the CLI defaulted to a "trusted" state if no specific setting was found. While convenient, this posed a security risk: if a user opened a repository containing malicious tool configurations, the CLI might have executed them without sufficient barriers.

Additionally, the Policy Engine had a limitation regarding "Modes." While system-level policies could restrict tools based on the CLI's operating mode (e.g., allowing specific tools only during autonomous editing), user-defined (Tier 2) and admin-defined (Tier 3) policies were restricted from using this property. This discrepancy limited users from creating context-specific workflows—for example, allowing `git rebase` during an autonomous session but blocking it during standard chat interactions.

### The Solution: Explicit Verification & Policy Parity
*   **PR #15943** flips the default boolean for folder trust. By default, `isTrustedFolder()` now returns `untrusted`. This ensures that potentially malicious tool execution is blocked in unknown environments until the user consciously opts in.
*   **PR #15977** removes the validation restriction in `toml-loader.ts`, enabling the `modes` property for all policy tiers. This aligns the actual behavior with the documentation and empowers users to define when exactly a tool should be accessible.

## 3. How-To Guide

### Managing Folder Trust
When you open a new project or folder that hasn't been configured, the Gemini CLI will now treat it as **Untrusted**.

1.  **Detection:** When you attempt to use Gemini features in a new folder, the CLI will block tool execution.
2.  **The Dialog:** You will be presented with the **Folder Trust Dialog**.
3.  **Action:**
    *   Select **Trust** to enable full tool execution.
    *   Select **Don't Trust** to enter a restricted mode where tools cannot run.
    *   *Note:* The CLI is smart enough to determine if a restart is required to reload the secure context. If you switch from Untrusted to Trusted, the application may restart automatically.

### Configuring Policies with 'Modes'
You can now scope permissions to specific CLI modes in your `.gemini/allowed-tools.toml` (or user policy file).

**Example Scenario:** You want to allow Gemini to perform Git operations only when it is in `autoEdit` mode, preventing accidental commits during a standard chat.

**In your `allowed-tools.toml`:**

```toml
# Allow 'git checkout' ONLY when in 'autoEdit' or 'yolo' mode
[[rules]]
action = "allow"
command = "git"
args = ["checkout"]
modes = ["autoEdit", "yolo"]

# Allow 'ls' in all modes (no mode restriction specified)
[[rules]]
action = "allow"
command = "ls"
```

## 4. Walkthrough / Technical Deep Dive

### Deep Dive: Folder Trust Logic
The security enhancement in **PR #15943** is centered around the `isTrustedFolder()` method.
*   **Previous Logic:** If `trustSetting === undefined`, return `true` (Trusted).
*   **New Logic:** If `trustSetting === undefined`, return `false` (Untrusted).

The update also includes a robust restart mechanism. The `useFolderTrust` hook now tracks state transitions. If the CLI detects a transition that alters the security context (e.g., Implicit Untrusted $\rightarrow$ Explicit Trusted), it triggers a reload of the secure context to ensure the new permissions are applied cleanly without residual state.

### Deep Dive: Policy Tier Validation
In **PR #15977**, the change was primarily inside the configuration loader (`toml-loader.ts`).
*   The loader processes policies in tiers: System (Tier 1), User (Tier 2), and Admin (Tier 3).
*   Previously, an explicit validation step checked if `modes` was present in Tier 2/3 files and threw a validation error if found.
*   This check has been removed, and the rule transformation logic was updated to preserve the `modes` property as it flows through the configuration merging process.
