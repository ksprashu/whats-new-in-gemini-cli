# 🚀 What's New: Persistent "Always Allow" Policies

**Release Date:** *[Current Date]*
**Contributors:** @allenhutchison
**Reference:** [PR #14737](https://github.com/google-gemini/gemini-cli/pull/14737)

## 1. Feature Summary
The Gemini CLI now supports **Persistent "Always Allow" Policies**. This feature removes the friction of repetitive approval prompts by allowing developers to save their authorization decisions for tool executions.

Key capabilities include:
*   **One-Click Persistence:** A new UI option to "Always allow and save to policy" directly from the confirmation prompt.
*   **Granular Shell Control:** Define security boundaries by whitelisting specific command prefixes and argument patterns (e.g., allow `git status` but prompt for `git push`).
*   **Multi-Cloud Platform (MCP) Support:** Distinct policy management for tools originating from different MCP servers.

## 2. Background & Context
**The Problem: Approval Fatigue**
Prior to this change, the Gemini CLI prioritized security by requiring explicit user confirmation for tool executions (like running shell commands or reading files). While secure, this created significant friction during repetitive workflows. Users frequently reported having to approve the same benign commands (like `ls`, `git status`, or linter checks) multiple times in a single session, interrupting their "flow state."

**The Solution**
PR #14737 introduces a configuration layer that persists user trust. By moving from a session-based approval model to a configuration-based policy model, we allow developers to define a "Safe Zone" for tools they use daily. This strikes a balance between security (granular control) and usability (reduced noise).

## 3. How-To Guide

### Using the Feature in the CLI
1.  **Trigger a Tool:** Ask Gemini to perform a task that requires a tool, such as listing files.
    > `> list the files in the src directory`
2.  **The New Prompt:** You will see an updated confirmation menu.
3.  **Select Persistence:** Instead of selecting "Yes", choose the new option:
    > **[Always allow and save to policy]**
4.  **Verification:** The tool runs immediately. The next time you ask Gemini to run that specific command (or a command matching the pattern), it will execute automatically without interrupting you.

### Manual Configuration
You can also manually edit your Gemini configuration file to pre-approve complex patterns.

**Example: Allowing specific Git commands**
To allow `git status` commands but keep other git commands behind an approval wall:

```json
{
  "toolPolicies": [
    {
      "tool": "shell_execute",
      "policy": {
        "commandPrefix": "git",
        "argsPattern": "^status.*",
        "action": "allow"
      }
    }
  ]
}
```

## 4. Walkthrough / Technical Deep Dive
Under the hood, this feature refactors how the CLI evaluates permission requests. Here is the logic flow introduced in the PR:

### 1. The Policy Engine
The update extends the configuration schema to support a `policies` array. When a tool is invoked, the CLI checks this array before prompting the user.

### 2. Granular Shell Matching
For shell tools, simple string matching isn't enough for security. The PR introduces two specific matchers:
*   **`commandPrefix`**: Checks the executable or primary command (e.g., `npm`).
*   **`argsPattern`**: Uses regex-style matching to validate arguments. This is crucial for preventing "over-permissioning."
    *   *Scenario:* You want to allow the CLI to read logs, but not delete them.
    *   *Implementation:* You can allow `cat *.log` via patterns while keeping `rm *.log` restricted, even though they both interact with the same file types.

### 3. MCP (Multi-Cloud Platform) Identity
With the rise of the Model Context Protocol (MCP), tools often share names but live on different servers. The update adds `mcpName` to the policy structure. This ensures that allowing a tool named `deploy` on your **Local Dev MCP** does not accidentally authorize a tool named `deploy` on your **Production MCP**.

### 4. UI/UX Integration (`ToolConfirmationMessage`)
The `ToolConfirmationMessage` UI component was updated to handle the write-back logic. When "Always allow" is selected, the CLI analyzes the current command request, generates the appropriate granular policy (extracting the command and args), and appends it to the global configuration file dynamically.
