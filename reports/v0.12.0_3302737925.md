# 🚀 What's New: The Codebase Investigator Subagent

**Release:** Gemini CLI (Latest)
**Contributors:** @abhipatel12, @silviojr

## 1. Feature Summary
We are excited to introduce the **Codebase Investigator Subagent**, a powerful new experimental feature for the Gemini CLI.

Previously, Gemini relied heavily on the context you manually provided (open files or highlighted code). The new Codebase Investigator is an autonomous subagent designed to actively explore your workspace. When you ask a broad question about your project, this subagent can navigate your file system, read relevant code, and resolve the necessary information to answer complex queries without requiring you to manually locate the specific files first.

## 2. Background & Context
**The Challenge:**
As projects grow, "context window management" becomes a cognitive burden for developers. Users frequently ask high-level questions (e.g., *"How is authentication handled in this app?"*) but may not know exactly which files contain the relevant logic. If the right files aren't in the context, the CLI's answers can be generic or hallucinated.

**The Solution (PR #9988):**
This feature shifts the burden of context discovery from the user to the CLI. By integrating a "Subagent" architecture, we have essentially given Gemini a research assistant.

The pull request lays the foundational groundwork for integrating experimental subagents. Instead of a monolithic architecture, the team introduced a modular system where subagents are registered as **tools**. This allows the main Gemini model to delegate tasks—specifically codebase exploration—to a specialized agent.

**Key Architectural Improvements:**
*   **Modularity:** The implementation resolves critical circular dependencies (specifically involving `Config`, `AgentRegistry`, and `CodebaseInvestigatorAgent`) by decoupling tool names into a dedicated `tool-names.ts` module.
*   **Security & Policy:** The implementation ensures that the `MessageBus` propagates correctly to subagents. This is vital for policy enforcement, ensuring that even autonomous subagents respect user permissions and confirmation flows before executing actions.

## 3. How-To Guide

### Enabling the Subagent
Because this feature is currently experimental, it may need to be enabled manually depending on your version defaults.

**Option A: Via Settings Menu**
1.  Open the Gemini CLI settings:
    ```bash
    /settings
    ```
2.  Navigate to the **Experimental** or **Agents** section (depending on your UI version).
3.  Toggle **Codebase Investigator** to `Enabled`.
4.  (Optional) Adjust the **Max Turns** setting. This limits how many steps the agent can take (e.g., searching 5 files vs. 20 files) to manage latency and token usage.

**Option B: Via `settings.json`**
For power users, you can configure this directly in your `settings.json` file.
```json
{
  "experimental": {
    "enableSubagents": true,
    "subagentSettings": {
      "codebaseInvestigator": {
        "maxTurns": 10
      }
    }
  }
}
```

### Using the Feature
Once enabled, you do not need to invoke a special command. Simply ask questions that require knowledge of the broader codebase.

**Example Prompt:**
> "Where is the validation logic for user sign-ups, and does it check for password complexity?"

**What happens:**
Instead of guessing, you will see an indicator that the **Codebase Investigator** is running. It will:
1.  Search file names for "auth", "user", "validation".
2.  Read the contents of the most relevant files.
3.  Return the specific findings to the main chat interface.

## 4. Walkthrough / Technical Deep Dive

For the developers and contributors interested in how this works under the hood, the architecture introduced in PR #9988 is a significant step forward in "Agentic" workflows.

### The "Agent as a Tool" Pattern
The core innovation here is wrapping an autonomous agent inside a `SubagentToolWrapper`. To the main Gemini model, the Codebase Investigator looks just like any other tool (like `fs.read` or `terminal.execute`).

1.  **Orchestration (`AgentExecutor`):** When the main model decides it needs to explore the code, it calls the subagent tool. This spins up an `AgentExecutor`—a dedicated loop that manages the subagent's "Thought → Action → Observation" cycle.
2.  **Registration (`AgentRegistry`):** The system dynamically registers defined subagents within the core `Config` when `enableSubagents` is true.
3.  **Execution (`SubagentInvocation`):**
    *   The subagent receives the user's query.
    *   It autonomously decides which files to list, read, or search using its own set of allowed tools.
    *   It continues this loop until it satisfies the query or hits the `maxTurns` limit.
4.  **Safety (`MessageBus` Integration):**
    *   A major technical hurdle was ensuring the subagent doesn't go rogue. The PR ensures the `MessageBus` is passed down to the subagent.
    *   If the subagent attempts an action that requires user confirmation (e.g., editing a file, though currently focused on investigation), the existing policy enforcement mechanisms trigger standard user confirmation prompts.
