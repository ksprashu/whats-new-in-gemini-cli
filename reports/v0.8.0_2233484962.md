# 🚀 What's New: The Gemini CLI Extension Ecosystem

## 1. Feature Summary
The Gemini CLI has officially graduated from a standalone tool to an extensible **platform**. With the introduction of the `gemini extensions` command suite, we have enabled full lifecycle management for add-ons.

This release introduces three critical subcommands:
*   **`list`**: View all locally installed extensions and their current versions.
*   **`update`**: Upgrade specific extensions or bulk-update all installed tools to their latest release.
*   **`new`**: A scaffold generator that allows developers to create, test, and ship their own Gemini extensions in seconds.

## 2. Background & Context
**Why was this change made?**
Previously, adding custom functionality to the Gemini CLI required waiting for core updates or using hacky shell aliases to pipe data into the CLI. As the user base grew, so did the demand for niche integrations (e.g., connecting Gemini to specific internal databases, proprietary APIs, or custom formatting tools).

**The Problem:**
*   **Bloat:** We cannot add every requested feature to the core binary without impacting performance and maintainability.
*   **Stale Tools:** Users maintaining custom scripts had no standardized way to version or update them.
*   **High Barrier to Entry:** Creating a tool that interfaces with the Gemini CLI required complex boilerplate setup.

**The Solution:**
This update creates a standardized plugin architecture. The `new` command solves the "Barrier to Entry" by scaffolding the boilerplate. The `list` and `update` commands solve the "Stale Tools" problem by introducing version management. This decouples the core CLI release cycle from community innovation.

## 3. How-To Guide

Here is how you can utilize the new Extension management commands.

### A. Managing Installed Extensions

**Listing Extensions**
To see what tools you currently have installed, use the `list` command. It displays the extension name, current version, and installation status.

```bash
$ gemini extensions list

NAME             VERSION   STATUS
gemini-sql       v1.0.2    Installed
gemini-format    v0.9.0    Installed
gemini-weather   v1.1.0    Update Available (v1.2.0)
```

**Updating Extensions**
You can update a specific extension by name, or omit the name to attempt an update for all installed extensions.

```bash
# Update a specific extension
$ gemini extensions update gemini-weather
✓ Successfully updated gemini-weather from v1.1.0 to v1.2.0

# Update all extensions
$ gemini extensions update
✓ gemini-sql is already up to date.
✓ gemini-format is already up to date.
```

## 4. Walkthrough / Technical Deep Dive

Under the hood, the `gemini extensions` architecture relies on a manifest-based discovery system.

### The `new` Scaffolding
When running `gemini extensions new`, the CLI pulls from internal templates. It generates a directory structure containing a `manifest.json` (or `extension.yaml`) file. This manifest defines:
*   **Entry Point:** The script or binary to execute.
*   **Permissions:** (e.g., Does this extension need network access?).
*   **Commands:** How the extension is invoked via the CLI (e.g., `gemini jira summarize`).

### The `list` Logic
The CLI scans the standard installation directory (typically `~/.config/gemini/extensions` on Linux/Mac or `%AppData%/gemini/extensions` on Windows). It parses the manifests of subdirectories to populate the list. It compares the local version hash against the remote registry (defined in the manifest) to determine if an "Update Available" flag is needed.

### The `update` Mechanism
Unlike a full system package manager, the `update` command is lightweight.
1.  It checks the remote repository defined in the extension's manifest.
2.  It downloads the latest release tarball.
3.  It verifies the checksum.
4.  It performs an atomic swap: unpacking the new version into a temp folder and renaming it to replace the old folder only if the unpack succeeds.
