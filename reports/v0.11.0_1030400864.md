# What’s New in Gemini CLI: Centralized Telemetry Configuration

## 1. Feature Summary
The Gemini CLI has undergone a significant configuration cleanup. Support for command-line flags related to telemetry (such as `--telemetry-otlp-endpoint` and `--telemetry-log-prompts`) has been removed.

Moving forward, all telemetry configurations must be managed via the `settings.json` file. This change removes deprecated arguments to streamline the CLI interface and enforce a "single source of truth" for persistent configuration settings.

## 2. Background & Context
**Why was this change made?**
Previously, the Gemini CLI allowed users to configure telemetry in multiple ways, specifically via long command-line arguments. Over time, these flags became deprecated as the tool matured toward a file-based configuration model.

According to **PR #11318**, the primary motivations for this change were:
*   **Simplification:** The argument parsing logic within the CLI was becoming cluttered with configuration options that are better suited for static files.
*   **Centralization:** By forcing configuration into `settings.json`, the CLI reduces the surface area for configuration options directly on the command line.
*   **Consistency:** This aligns telemetry configuration with other persistent settings in the ecosystem, ensuring users don't have to mix-and-match CLI flags with JSON config files.

## 3. How-To Guide
If you were previously running automation scripts or local commands using the `--telemetry-*` flags, your commands will now fail. You must migrate these settings to your `settings.json` file.

### Migration Example

**❌ Old Way (Command Line):**
```bash
gemini chat "Hello" \
  --telemetry \
  --telemetry-otlp-endpoint="http://localhost:4317" \
  --telemetry-log-prompts
```

**✅ New Way (`settings.json`):**
1.  Open or create your `settings.json` file (typically located in `.gemini/` or your user configuration directory).
2.  Add the telemetry configuration object. *Note: Keys typically map to the old flag names in camelCase.*

```json
{
  "telemetry": {
    "enabled": true,
    "otlpEndpoint": "http://localhost:4317",
    "otlpProtocol": "grpc",
    "logPrompts": true,
    "outfile": "./telemetry-log.json"
  }
}
```

3.  Run your command cleanly:
```bash
gemini chat "Hello"
```

### Removed Flags Reference
The following flags are no longer valid:
*   `--telemetry`
*   `--telemetry-target`
*   `--telemetry-otlp-endpoint`
*   `--telemetry-otlp-protocol`
*   `--telemetry-log-prompts`
*   `--telemetry-outfile`

## 4. Walkthrough / Technical Deep Dive
This change is primarily a refactor of the CLI's entry point and argument parser.

1.  **Argument Parsing:** The code responsible for parsing `argv` has been stripped of the definitions for the telemetry flags. If a user attempts to pass these flags, the underlying CLI framework will likely throw an "unknown argument" error immediately.
2.  **Initialization Flow:** Previously, the telemetry service likely initialized by checking CLI args first, then falling back to config files. Now, the initialization logic points exclusively to the settings loader.
3.  **Test Suite Overhaul:** As noted in the PR, the test suite was significantly updated. Tests that verified that passing `--telemetry-outfile` resulted in a file being created have been rewritten to verify that setting the equivalent value in the mocked `settings.json` produces the file.

This shift suggests that the Gemini CLI is moving toward a standard "Config-driven Development" architecture, where the CLI binary is the engine, and `settings.json` is the control panel, rather than passing all controls in via the terminal at runtime.
