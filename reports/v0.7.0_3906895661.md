# Feature Spotlight: Enhanced Tool Visibility in Chat Sharing
**Release:** Gemini CLI Update | **Contributor:** @rramkumar1

## 1. Feature Summary
The Gemini CLI has significantly improved its session export capabilities. The `/chat share` command, used to export current conversation histories to Markdown, now includes **full support for Tools (Function Calling)**.

Previously, exported logs often captured only the conversational text between the User and the Model, skipping the intermediate technical steps. With this update, both the **function calls** generated by the model and the subsequent **function responses** are rendered directly in the final Markdown file. This ensures that shared chat logs represent the complete execution logic of the agent.

## 2. Background & Context
**The Problem:**
As developers increasingly use Gemini for agentic workflows (where the model uses tools to query databases, check APIs, or run code), the debugging process became fragmented.
*   Users would ask a question (e.g., "What is the weather in Tokyo?").
*   The Model would call a tool behind the scenes and answer ("It is currently raining").
*   When running `/chat share`, the markdown file would only show the question and the final answer. The actual JSON payload sent to the API and the raw data returned were lost in the export. This created a "black box" effect, making it difficult to audit *why* the model gave a specific answer when sharing logs with teammates.

**The Solution:**
This change (linked to PR #8693 and Issue #8030) bridges the gap between runtime execution and documentation. By serializing the tool interaction steps into the Markdown export, developers get a verifiable audit trail of the model's logic and the data it acted upon.

## 3. How-To Guide
Here is how to utilize the new feature to audit an agentic workflow.

### Prerequisites
Ensure you have the latest version of the Gemini CLI installed and a tool/function definition loaded into your session.

### Step-by-Step
1.  **Start a Session with Tools:**
    Initialize a chat that has access to a function (e.g., a weather lookup or database query).

2.  **Trigger the Tool:**
    Ask a question that forces the model to use the tool.
    ```bash
    >>> What's the stock price of GOOGL right now?
    ```
    *(The CLI internally calls the `get_stock_price` function and returns JSON data).*

3.  **Export the Session:**
    Run the share command.
    ```bash
    >>> /chat share
    ```

4.  **Review the Artifact:**
    Open the generated Markdown file. You will now see a structure similar to this:

    > **User:** What's the stock price of GOOGL right now?
    >
    > **Model (Function Call):**
    > ```json
    > {
    >   "name": "get_stock_price",
    >   "args": { "ticker": "GOOGL" }
    > }
    > ```
    >
    > **Tool (Response):**
    > ```json
    > {
    >   "price": "178.35",
    >   "currency": "USD"
    > }
    > ```
    >
    > **Model:** The current stock price for GOOGL is $178.35 USD.

## 4. Walkthrough / Technical Deep Dive
Under the hood, the `/chat share` command iterates through the session history maintained in memory.

**Previously:**
The iterator likely filtered for messages with `role: "user"` or `role: "model"` containing content text. It ignored messages associated with `role: "function"` or model parts strictly containing `function_call`.

**Now:**
The rendering engine has been updated to handle the multi-turn complexity of tool use:
1.  **Detection:** The parser scans the history for `part` objects that contain `functionCall` or `functionResponse`.
2.  **Formatting:**
    *   **Function Calls:** When the model outputs a call, the CLI formats the function name and arguments into a syntax-highlighted JSON code block.
    *   **Function Responses:** The return values from the client-side code are similarly captured and formatted.
3.  **Sequence Preservation:** The CLI ensures these blocks are inserted chronologically between the user prompt and the final model text response, preserving the causal chain of the conversation.
