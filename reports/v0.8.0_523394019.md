# 🚀 What's New: Introducing Gemini CLI Extensions

## 1. Feature Summary
The Gemini CLI has officially moved from a static toolset to an extensible platform. With the introduction of **Gemini CLI Extensions**, developers can now build, share, and install custom commands that live alongside the core native commands.

This feature allows the community to extend the capabilities of the Gemini CLI without waiting for upstream releases, enabling custom workflows, niche API integrations, and domain-specific prompt engineering tools to be treated as first-class citizens within the terminal.

## 2. Background & Context
**Why was this change made?**
Previously, adding functionality to the Gemini CLI required modifying the core Go/Python codebase, submitting a Pull Request, and waiting for a release cycle. As detailed in the initial RFCs (Request for Comments), this monolithic approach created two main problems:
1.  **Feature Bloat:** The core binary was at risk of becoming heavy with niche features that only a small percentage of users needed.
2.  **Velocity Bottlenecks:** Developers wanted to experiment with new Gemini API modalities rapidly without the friction of the core contribution process.

**The Solution**
By adopting a federated extension model (inspired by the GitHub CLI `gh extension` logic), the core CLI remains lightweight. It delegates specialized tasks to external repositories. This shift empowers the community to build "opinionated" tools—such as a specific log analyzer or a code-refactoring agent—that can be installed on demand.

## 3. How-To Guide

### Installing an Extension
Extensions are repository-based. To install a tool built by another developer, use the new `extension` namespace.

```bash
# Syntax: gemini extension install <owner>/<repo>
gemini extension install google-gemini/gemini-git-helper
```

Once installed, the command becomes available globally:

```bash
gemini git-helper --commit-msg
```

### Building Your Own Extension
Creating an extension is straightforward. An extension is simply a local binary or script prefixed with `gemini-`.

**Step 1: Create the script**
Create a file named `gemini-hello` (or `gemini-hello.sh`).

```bash
#!/bin/bash
# A simple extension to greet the user via Gemini
echo "Hello! I am a custom extension. Asking Gemini for a fun fact..."
gemini prompt "Tell me a short fun fact about space."
```

**Step 2: Make it executable**
```bash
chmod +x gemini-hello
```

**Step 3: Install locally**
You can install from a local directory for development.
```bash
gemini extension install .
```

**Step 4: Run it**
```bash
gemini hello
```

## 4. Walkthrough / Technical Deep Dive
**How it works under the hood:**

1.  **Discovery:** When you run `gemini <command>`, the CLI first checks its internal registry of native commands. If no match is found, it scans the user's extension directory (typically `~/.config/gemini/extensions`).
2.  **The Manifest:** Extensions require a `gemini-extension.yaml` manifest file in the root of the repository. This file defines the entry point and metadata.
    ```yaml
    name: git-helper
    version: 1.0.0
    entry_point: bin/gemini-git-helper
    description: "AI-assisted git workflows"
    ```
3.  **Execution (IPC):** The Gemini CLI executes the extension as a subprocess. It passes `stdin`, `stdout`, and `stderr` through to the extension. Crucially, the extension inherits the **Authentication Context**. The main CLI exports the API key and session tokens as environment variables (`GEMINI_API_KEY`, etc.) to the subprocess, so extension authors do not need to implement their own auth flow.
