# What’s New: OpenTelemetry GenAI Semantic Conventions

## 1. Feature Summary
The Gemini CLI has significantly upgraded its observability capabilities by adopting **OpenTelemetry (OTel) GenAI Semantic Conventions**. 

This update moves the CLI’s telemetry from generic reporting to industry-standard metrics specifically designed for Generative AI. Users can now stream precise data regarding **token usage** (input/output) and **operation duration** directly to their monitoring dashboards. This ensures that the Gemini CLI integrates seamlessly with the broader observability ecosystem (like Prometheus, Grafana, or Honeycomb) without requiring custom data transformation.

## 2. Background & Context
**The Problem:**
As developers move GenAI workflows from experimentation to production, observability becomes critical. Previously, telemetry within the Gemini CLI provided general usage insights, but it lacked specific alignment with the rapidly evolving standards for LLM monitoring. This made it difficult for platform engineers to correlate Gemini CLI operations with other services or to accurately track costs (tokens) and latency using standard tools.

**The Solution:**
Addressed in **PR #10343** (and linked to **Issue #9212**), this change implements the OpenTelemetry GenAI Semantic Conventions.
*   **Interoperability:** By adhering to the official OTel spec, the CLI now speaks the same language as other GenAI frameworks and monitoring tools.
*   **Granularity:** We have moved beyond "did it work?" to "how many tokens did it cost?" and "exactly how long did the generation take?"
*   **Standardization:** This update future-proofs the CLI, ensuring that as the OTel spec evolves, the metrics remain consistent with the industry.

## 3. How-To Guide

To leverage these new metrics, you generally need to have your telemetry exporter configured (standard OTel environment variables usually apply).

### Step 1: Configuration
Ensure your environment is set up to export OTel data. While the CLI handles the collection, you need a destination.
```bash
# Example configuration (depending on your OTel collector setup)
export OTEL_EXPORTER_OTLP_ENDPOINT="http://localhost:4317"
export OTEL_SERVICE_NAME="gemini-cli"
```

### Step 2: Running Commands
Use the Gemini CLI as you normally would. The metrics are recorded automatically in the background during standard operations.

```bash
# Run a prompt
gemini prompt "Explain the theory of relativity in one sentence."
```

### Step 3: Visualizing the Data
In your observability backend (e.g., Grafana, Jaeger), search for the new semantic attributes. You will no longer look for generic event names but rather standard GenAI keys.

**Look for these specific Metrics:**
*   `gen_ai.client.token.usage`: Breakdown of prompt tokens vs. completion tokens.
*   `gen_ai.client.operation.duration`: Latency of the request in milliseconds.

## 4. Walkthrough / Technical Deep Dive

The engineering work behind this feature focuses on two core packages: `packages/core/src/telemetry/metrics.ts` and `loggers.ts`.

### The "Semantic" Shift
The core change involves mapping internal CLI events to OTel Semantic Conventions. instead of recording a generic `metric_request_success`, the system now records attributes defined by the GenAI spec.

**Key Implementation Details:**

1.  **Metric Definitions:**
    New enums were created to strictly define the metric names, preventing typo-induced telemetry black holes. This ensures that `gen_ai.client.token.usage` is always spelled correctly across the codebase.

2.  **Instrumentation Logic (`loggers.ts`):**
    The logging logic was updated to intercept the response payload from the Gemini API.
    *   **Token Counting:** It extracts `inputTokenCount` and `outputTokenCount` from the API response and records them under the standard `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens` attributes.
    *   **Duration Tracking:** It measures the delta between the request start and response end, recording it as a histogram under `gen_ai.client.operation.duration`.

3.  **Error Handling:**
    The telemetry logic distinguishes between successful generations and API errors, tagging the metrics with `error.type` attributes where necessary. This allows for creating "Success Rate" dashboards specifically for GenAI calls.

4.  **Documentation:**
    The `docs/telemetry.md` file has been updated to act as a reference guide for these new keys, ensuring teams know exactly what strings to query in their dashboards.
