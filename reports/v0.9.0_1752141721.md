# What’s New in Gemini CLI: Pre-Release Extension Support

**Contributor:** @jakemac53  
**Pull Request:** [#10752](https://github.com/google-gemini/gemini-cli/pull/10752)  
**Related Issue:** [#8654](https://github.com/google-gemini/gemini-cli/issues/8654)

---

## 1. Feature Summary
The `gemini extensions install` command has been upgraded to support a new `--pre-release` flag. This enhancement allows developers and early adopters to install the absolute latest version of an extension from GitHub, even if that version is marked as a "pre-release" (e.g., alpha, beta, or release candidates) and has not yet been promoted to the "latest" stable tag.

## 2. Background & Context
**The Problem:**
Previously, the Gemini CLI’s extension installer was designed to prioritize stability. When fetching an extension from GitHub, it strictly looked for the release tagged as `latest`. 

However, this created friction for extension authors and QA testers. As highlighted in **Issue #8654**, there was no easy way to opt-in to a newer version for testing purposes without manually marking it as "latest" on GitHub—which would inadvertently push potentially unstable code to all general users.

**The Solution:**
This update introduces a mechanism to opt-out of the "stable-only" constraint. By adding the `--pre-release` flag, the CLI instructs the internal fetch logic to retrieve the most recent release object created, regardless of its stability tag. This facilitates staged rollouts, allowing authors to test `v2.0.0-beta` in the wild while general users continue to receive the stable `v1.0.0`.

## 3. How-To Guide

Using the new feature is straightforward. It modifies the existing installation command.

### Syntax
```bash
gemini extensions install <extension-name> --pre-release
```

### Usage Example
Imagine an extension named `firebase-tools`.
*   **Current Stable Version:** `v1.0` (Marked "Latest" on GitHub)
*   **Current Beta Version:** `v1.1-beta` (Marked "Pre-release" on GitHub)

**To install the stable version (Default behavior):**
```bash
gemini extensions install firebase-tools
# Result: Installs v1.0
```

**To install the beta version (New behavior):**
```bash
gemini extensions install firebase-tools --pre-release
# Result: Installs v1.1-beta
```

## 4. Walkthrough / Technical Deep Dive
Under the hood, this change refactors how the CLI interacts with the GitHub API.

### Logic Flow
1.  **Command Invocation:** The user runs the install command. The CLI now parses a new boolean flag: `preRelease`.
2.  **API Routing:** This flag is passed down to the `fetchReleaseFromGithub` function.
3.  **Conditional Fetching:**
    *   **If `preRelease` is false:** The CLI queries the GitHub API specifically for the release tagged `latest`.
    *   **If `preRelease` is true:** The CLI queries the GitHub API for the *list* of releases and selects the first item (chronologically newest), effectively bypassing the "latest" filter.

### Code Refactoring
In addition to the logic change, this PR improved the codebase's modularity:
*   **New Module:** The utility logic for making HTTP requests to GitHub has been extracted into a dedicated file: `github_fetch.ts`. 
*   **Separation of Concerns:** This makes the `fetchJson` utility reusable across other parts of the CLI that might need to interact with GitHub in the future, while isolating the specific release-parsing logic.
*   **Validation:** New test cases were added to explicitly verify that the fetcher respects the boolean flag and targets the correct JSON endpoint on GitHub.
