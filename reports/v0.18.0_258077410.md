# 🚀 What’s New in Gemini CLI: The Policy Engine (Experimental)

**Date:** November 2025
**Status:** Experimental / Flag-gated

## 1. Feature Summary
The Gemini CLI is introducing a new **Policy Engine**, a robust security layer designed to govern tool use and autonomous agent behavior.

Previously, granting the CLI access to tools (like file system access or Google Workspace connectors) was often binary: the model could either use the tool or it couldn't. With this update, users and administrators can define **fine-grained policies**. You can now restrict arguments, define specific allowed paths, or require human confirmation for high-stakes actions, all configured via a declarative policy file.

This feature is currently experimental and must be enabled via a feature flag.

## 2. Background & Context
**Why was this change made?**
As Large Language Models (LLMs) transition from chat interfaces to "Agents" capable of executing code and manipulating files, the security surface area expands significantly.

*   **The Problem:** "Autonomy without Guardrails." Users want the Gemini CLI to automate complex tasks (e.g., "Clean up my Downloads folder"), but they worry about the model hallucinating and deleting critical system files.
*   **The Solution:** A middleware Policy Engine. Instead of relying solely on the LLM's internal safety training, the CLI now enforces hard-coded rules on the client side *before* a tool execution occurs.
*   **The Philosophy:** As detailed in the associated blog post, *"The Guardrails of Autonomy,"* trust in AI agents is built on verifiable boundaries. This feature moves the CLI from a "pilot" mode to a "copilot with flight envelope protection" mode.

## 3. How-To Guide

### Prerequisites
*   Update to the latest version of Gemini CLI.
*   Prepare a policy configuration file (YAML or JSON).

### Step 1: Define your Policy
Create a file named `gemini-policy.yaml`. In this example, we will allow the CLI to read files anywhere, but only allow it to *write* files inside a specific temporary directory.

```yaml
version: "1.0"
policies:
  - tool: "fs_read"
    action: "allow"
  - tool: "fs_write"
    action: "allow"
    conditions:
      - field: "path"
        operator: "starts_with"
        value: "./tmp/"
  - tool: "fs_delete"
    action: "deny" # Hard block on deletion for safety
```

### Step 2: Run with the Experimental Flag
Since this is experimental, you must pass the policy flag when invoking the CLI.

```bash
gemini chat \
  --experimental-policy-engine \
  --policy-file ./gemini-policy.yaml \
  --prompt "Summarize the logs in ./logs/ and write the report to ./tmp/report.txt"
```

### Step 3: Verify Behavior
If you ask the CLI to write to a protected directory:
`> "Write the report to /etc/config.txt"`

The CLI will return a system error to the model (and the user console) stating:
`[Policy Engine] Blocked: Write access denied for path '/etc/config.txt'.`

## 4. Walkthrough / Technical Deep Dive

The Policy Engine functions as an **interceptor pattern** between the LLM's reasoning loop and the actual Tool Execution Runtime.

1.  **Intent Generation:** The Gemini model decides it needs to call a tool (e.g., `fs_write`). It generates the function call and arguments.
2.  **Interception:** The CLI pauses execution. It does not run the tool yet.
3.  **Policy Evaluation:**
    *   The CLI parses the active `gemini-policy.yaml`.
    *   It matches the requested tool name (`fs_write`) against the rules.
    *   It evaluates conditional logic (e.g., Does the `path` argument match the regex or `starts_with` rule?).
4.  **Decision:**
    *   **ALLOW:** The tool executes, and the output is fed back to the model.
    *   **DENY:** The execution is skipped. A structured error message is injected back into the context window, allowing the LLM to self-correct (e.g., "I apologize, I do not have permission to write there. Shall I use the ./tmp folder instead?").
    *   **CONFIRM (Future/Roadmap):** The CLI pauses and prompts the user `[y/N]` to manually authorize the specific action.
