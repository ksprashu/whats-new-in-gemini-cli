# 🚀 What's New in Gemini CLI: Configurable Compression

**PR:** [#12317](https://github.com/google-gemini/gemini-cli/pull/12317) | **Author:** @scidomino | **Release Impact:** Performance & Configuration

## 1. Feature Summary
We have introduced **Configurable Compression Thresholds** to the Gemini CLI. Users can now fine-tune exactly when the CLI compresses request payloads via the `/settings` menu. Additionally, out of the box, the CLI is now **more proactive**, applying compression to smaller payloads by default to improve latency and data efficiency without requiring manual user intervention.

## 2. Background & Context
**The Problem:**
Previously, the logic determining when to compress a prompt or file context before sending it to the Gemini API was likely hardcoded or set to a high threshold. This meant that medium-sized requests were being sent as raw text, potentially leading to:
*   Higher network latency.
*   Slower "Time to First Token" (TTFT).
*   Inefficient bandwidth usage on slower connections.

**The Solution:**
Addressed in **PR #12317** and tracked in **Issue #973**, this update exposes the compression logic to the user. By moving this configuration to `/settings`, we empower developers to optimize the CLI for their specific network environments. Furthermore, by lowering the default threshold (making it "more proactive"), the team has optimized the average user experience, ensuring that payload optimization kicks in earlier.

## 3. How-To Guide

Here is how you can adjust the compression settings in your CLI environment.

### Accessing the Setting
1.  Open your terminal.
2.  Run the settings command (assuming standard CLI slash-command syntax):
    ```bash
    gemini /settings
    ```
3.  Navigate to the **Network** or **Performance** section (depending on your specific UI layout).
4.  Look for a setting labeled **`Compression Threshold`** (or similar).

### Configuration Examples

*   **The New Default (Proactive):**
    If you leave the setting alone, the CLI will now compress payloads earlier (e.g., perhaps at 1KB instead of 10KB). This is ideal for most users.

*   **For High-Bandwidth Environments (Local/Intranet):**
    If you want to avoid the CPU overhead of compression because your network is incredibly fast:
    *   Set the threshold to a **High Value** (e.g., `10000` or `Infinite`).

*   **For Low-Bandwidth Environments (Mobile/Slow WiFi):**
    *   Set the threshold to a **Low Value** (e.g., `500` bytes).
    *   *Result:* Almost every request will be compressed, saving bandwidth at the cost of a tiny amount of local CPU time.

## 4. Walkthrough / Technical Deep Dive

### Under the Hood
The change in **PR #12317** is extremely efficient, resulting in a net bundle size increase of only **+81 Bytes**.

*   **Logic Change:** The core change involves replacing a static integer (the old threshold) with a variable look-up against the user's config file.
*   **The Conditional:**
    ```javascript
    // Conceptual Logic
    const userThreshold = config.get('compressionThreshold') || DEFAULT_PROACTIVE_LIMIT;

    if (payloadSize > userThreshold) {
       payload = await compress(payload);
    }
    ```
*   **Sandbox Integrity:** The PR touched several macOS sandbox definition files (`.sb`), including `sandbox-macos-permissive-open.sb` and `restrictive-closed.sb`. However, the diff shows **0 Bytes** changed for these files.
    *   *Interpretation:* This indicates that while the build process touched or re-verified the sandbox definitions, no permissions were actually loosened or tightened. The compression utilizes existing allowed system libraries (likely `zlib` or similar) already permitted within the sandbox scope.
