# 🚀 Feature Spotlight: Sequential Tool Approval

**Version:** *Latest Build* | **PR:** [#11593](https://github.com/google-gemini/gemini-cli/pull/11593) | **Contributor:** @joshualitt

## 1. Feature Summary
The Gemini CLI has upgraded its interaction model for agents involving multiple steps. Previously, complex tasks might require batch approval or broad permissions. With **Sequential Approval**, the CLI now supports a granular, step-by-step "Human-in-the-loop" workflow. When Gemini needs to execute multiple tool calls (e.g., reading a file, then modifying a file, then running a test), it presents each action to the user for approval individually as they occur, rather than all at once.

## 2. Background & Context
**The Problem:**
In sophisticated CLI agent workflows, Large Language Models (LLMs) often generate a "chain of thought" requiring multiple distinct actions.
*   **The Old Way:** Users often had to grant "blanket approval" for a request, effectively saying, "Go ahead and do whatever you need to finish this task." This is risky if the model hallucinates a destructive command (e.g., `rm -rf`) in the middle of a chain.
*   **The Issue:** As referenced in Issue #11541, developers needed a way to interrupt or verify intermediate steps without stopping the entire session.

**The Solution:**
This change introduces a synchronous pause point between tool calls. It solves the safety gap by allowing the user to act as a gatekeeper for *every* significant state change. It ensures that the output of Tool A (e.g., `list_files`) is reviewed and approved before Tool B (e.g., `delete_file`) is ever presented to the execution environment.

## 3. How-To Guide
You don't need to install new dependencies, but you will notice a change in the interactive flow when using the CLI for multi-step tasks.

### Scenario: Refactoring a File
Imagine asking Gemini to "Find the `main.py` file and rename the class `OldName` to `NewName`."

**Step 1: Run your command**
```bash
gemini chat "Find main.py and rename class OldName to NewName"
```

**Step 2: First Approval (Search)**
Gemini will determine it needs to find the file first.
```text
> Gemini: I need to list files to locate main.py.
> Tool Call: list_directory('.')
> Approve this action? [Y/n]: Y
```
*The CLI executes the tool and feeds the file list back to the model.*

**Step 3: Second Approval (Read)**
```text
> Gemini: Found main.py. I need to read its content.
> Tool Call: read_file('main.py')
> Approve this action? [Y/n]: Y
```

**Step 4: Third Approval (Write/Refactor)**
```text
> Gemini: I am ready to replace the class name.
> Tool Call: write_file('main.py', content=...)
> Approve this action? [Y/n]: 
```
*Here, you can inspect the logic. If you change your mind, you can hit `n` to stop the write operation.*

## 4. Walkthrough / Technical Deep Dive
Under the hood, this change alters the execution loop of the CLI's `Agent` or `Runner` class.

1.  **Generation Phase:** The LLM generates a completion that includes a `function_call` (or tool use) stop sequence.
2.  **Interception:** Instead of automatically piping this call to the execution engine, the CLI halts the loop.
3.  **User Prompt:** The CLI parses the requested function name and arguments (e.g., `fs.write`) and renders a confirmation prompt to `stdout`.
4.  **Branching Logic:**
    *   **If Approved:** The CLI executes the function, captures the `return_value`, and appends a "Tool Output" message to the conversation history. The context window is updated, and the LLM is invoked again to determine the *next* step.
    *   **If Denied:** The CLI feeds a rejection signal (or a user-provided reason) back to the model. This allows the model to attempt a different strategy or gracefully apologize without having executed the code.

This sequential nature means the model receives the *actual result* of Step 1 before it even calculates Step 2, leading to higher accuracy compared to pre-planning all steps blindly.

## 5. Next Steps for Demos
As a Developer Advocate, here is how you should showcase this in your next video or tutorial:

*   **Demo 1: "The Safety Catch" (High Impact)**
    *   Ask Gemini to "Clean up my project."
    *   Show it listing files (Approve).
    *   Show it trying to delete a file you *don't* want deleted (e.g., `.env` or `README.md`).
    *   **Action:** Deny the specific delete call.
    *   **Result:** Show Gemini acknowledging the denial and skipping that file, proving the safety mechanism works.

*   **Demo 2: "Iterative Exploration"**
    *   Task Gemini with debugging a script where the error isn't obvious.
    *   Approve a `read_file` call.
    *   Show how the model reads the file, realizes it needs to check a second dependency file, and requests to read that one next.
    *   Highlight that the user is "riding along" with the debugger in real-time.
