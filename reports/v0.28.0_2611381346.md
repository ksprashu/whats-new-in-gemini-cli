# What’s New in Gemini CLI: Enhanced Auth Consent & Smart Bug Reporting

**Authors:** @ehedlund, @erikus  
**Components:** Authentication, Reporting  
**PRs:** [#17699](https://github.com/google-gemini/gemini-cli/pull/17699), [#17569](https://github.com/google-gemini/gemini-cli/pull/17569)

---

## 1. Feature Summary
This release focuses on user agency and developer efficiency. We have overhauled the **OAuth authentication flow** to prioritize user consent. The CLI will no longer surprise users by automatically launching a browser window; instead, it now requires explicit approval via an interactive prompt before initiating the OAuth handshake.

Additionally, we have upgraded the **Bug Reporting tool**. When submitting issues via the CLI, the system now automatically captures and includes the active authentication method. This small metadata addition significantly reduces the "back-and-forth" required between users and maintainers during debugging.

---

## 2. Background & Context

### The Problem: "Surprise" Browser Windows
Previously, when the Gemini CLI needed to authenticate or refresh a token via OAuth, it would immediately spawn a browser window to the Google login page.
*   **Context:** As discussed in PR #17699, this behavior could be jarring or perceived as intrusive, especially if the user wasn't expecting an immediate network call.
*   **Solution:** By introducing an explicit consent step, we align with CLI best practices—ensuring the user is always in control of when the tool interacts with the browser or external networks.

### The Problem: Missing Context in Bug Reports
Debugging authentication issues is notoriously difficult without knowing *how* the user is logged in (e.g., Service Account vs. OAuth vs. API Key).
*   **Context:** Maintainers frequently had to ask issue reporters, "Which auth method are you using?" as a first triage step (PR #17569).
*   **Solution:** By programmatically injecting the active auth strategy into the report generated by `/bug`, we eliminate this triage step and accelerate resolution times.

## 3. How-To Guide

### Authenticating with the New Consent Flow
No configuration changes are required to enable this feature; it is now the default behavior for OAuth users.

**Step 1: Run a command requiring auth**
```bash
gemini chat "Hello world"
```

**Step 2: Interact with the Prompt**
Instead of immediately seeing Chrome/Safari open, you will now see a prompt in your terminal:
```text
? The Gemini CLI needs to open your browser to authenticate. Do you wish to proceed? (Y/n)
```

*   **Type `Y` (or Enter):** The browser launches, and authentication proceeds as normal.
*   **Type `n`:** The operation is cancelled gracefully without opening the browser.

### Generating Enhanced Bug Reports
If you encounter an issue, use the built-in bug command.

**Step 1: Run the bug command**
```bash
gemini bug
```

**Step 2: Review the Output**
The command will generate a report summary. Look for the `Authentication` field:

```text
Gemini CLI Bug Report
---------------------
OS: Darwin 23.0.0
Node: v20.10.0
...
Authentication: OAuth2 (User)  <-- NEW! Now automatically populated
...
```

## 4. Walkthrough / Technical Deep Dive

### The Consent Mechanism (PR #17699)
The engineering behind the consent flow is designed to be robust across different environments (Desktop vs. Headless).

1.  **Event-Driven Architecture:** The implementation utilizes a new `ConsentRequest` event. This decouples the core logic (OAuth) from the specific UI implementation.
2.  **Detection Logic:**
    *   **Interactive TTY:** If the CLI detects a terminal environment, it utilizes a `readline` prompt to capture keystrokes (Y/n).
    *   **GUI Wrapper:** If the CLI is running wrapped in a GUI (like an IDE extension), the `ConsentRequest` event can be caught by UI event listeners to render a native dialog box.
3.  **Safety Rails:**
    *   **Non-Interactive/Non-TTY:** If the CLI runs in a CI/CD pipeline where no user can type `Y`, the system throws a `FatalAuthenticationError`. This prevents the process from hanging indefinitely while waiting for input that will never come.

### Bug Report Integration (PR #17569)
This change modifies the `bugCommand.test.ts` and the report generator logic.
*   The system queries the `AppContainer` for the currently active `AuthStrategy`.
*   It serializes the strategy name (e.g., `OAuth`, `ServiceAccount`, `APIKey`) and appends it to the system environment block of the report.
*   **Security Note:** This only logs the *method* of authentication, not the tokens or keys themselves.

## 5. Next Steps for Demos

When showcasing these features in a video or team demo, consider the following flow:

1.  **The "Consent" Demo:**
    *   Logout of the CLI first.
    *   Run a command to trigger the flow.
    *   **Pause** at the `(Y/n)` prompt. Explain that previously, the browser would have already opened.
    *   Accept the prompt to show the successful flow.

2.  **The "Safety" Demo (Optional but technical):**
    *   Run a command in a way that simulates a non-interactive shell (e.g., piping to `/dev/null` or using a specific flag if available) to demonstrate the `FatalAuthenticationError`. This reassures DevOps engineers that scripts won't hang silently.

3.  **The "Support" Demo:**
    *   Run `gemini bug`.
    *   Highlight the new line item in the output. Explain how this helps the open-source maintainers help *you* faster.
