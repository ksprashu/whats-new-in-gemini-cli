# What’s New in Gemini CLI: Enforced Authentication

## 1. Feature Summary
System administrators and DevOps leads can now strictly control how users authenticate with the Gemini CLI. With the introduction of the `enforcedAuthType` configuration setting, you can mandate a specific authentication method (such as `oauth-personal` or `gemini-api-key`), effectively disabling all other login options for the end-user.

## 2. Background & Context
**The Problem:**
Previously, the Gemini CLI offered users a choice of authentication methods (Google OAuth, API Keys, etc.). While flexibility is great for individual developers, it poses challenges for enterprise environments where:
*   **Security Compliance:** Organizations may require all access to be mediated through a specific identity provider (OAuth) and forbid the use of static, long-lived API keys.
*   **Billing & Usage Tracking:** To ensure API usage is billed to the correct corporate account, admins need to prevent users from accidentally using personal credentials.
*   **Onboarding Simplicity:** Removing options reduces cognitive load and "paradox of choice" for new developers setting up their environment.

**The Solution:**
This update (PR #6564) introduces a governance layer within the `settings.json` file. By setting `enforcedAuthType`, the decision is made upstream by the administrator, ensuring the CLI behaves exactly as required by organizational policy.

## 3. How-To Guide

### Prerequisites
*   Gemini CLI installed (latest version).
*   Access to the user's configuration file (typically `~/.config/gemini/settings.json` or the system-wide equivalent).

### Configuration Steps

To enforce an authentication method, you need to modify the `settings.json` file.

**1. Open your settings file:**
```bash
nano ~/.config/gemini/settings.json
```

**2. Add the enforcement key:**
Add the `enforcedAuthType` property to the JSON object.

**Example A: Mandate Google OAuth**
This forces the user to sign in via the browser flow.
```json
{
  "enforcedAuthType": "oauth-personal"
}
```

**Example B: Mandate API Key**
This forces the user to provide a Gemini API Key.
```json
{
  "enforcedAuthType": "gemini-api-key"
}
```

**3. Verify the behavior:**
Run the login command:
```bash
gemini auth login
```
**Result:** Instead of seeing a list of options (OAuth, API Key, Enterprise), the CLI will immediately prompt for the enforced method or inform the user that only that method is allowed.

## 4. Walkthrough / Technical Deep Dive

Based on the code coverage report and file structure, here is how the enforcement logic is implemented under the hood:

### 1. Configuration Schema Update (`src/config/settings.ts`)
The `settings.json` schema has been updated to accept `enforcedAuthType`. This is likely a strict typed string union (e.g., `'oauth-personal' | 'gemini-api-key'`). When the CLI initializes, it parses this file using the logic in `src/config/settingsSchema.ts`.

### 2. The Authentication Dialog (`src/ui/components/AuthDialog.tsx`)
This component is responsible for rendering the interactive menu where users usually select their login method.
*   **Logic Change:** The component now checks the `Config` service for the presence of `enforcedAuthType`.
*   **UI Behavior:** If a value is detected, the "Selection" step is bypassed entirely. The component automatically routes the user to the specific sub-component (e.g., the OAuth flow or the API Key input prompt) associated with that type.

### 3. Command Enforcement (`src/ui/commands/authCommand.ts`)
The backend logic for the `auth` command has been hardened. Even if a user attempts to manually trigger a specific auth flag or bypass the UI, the command handler validates the attempt against the `enforcedAuthType` setting. This ensures that the enforcement is not just a UI cosmetic change, but a functional restriction.

### 4. Active Auth Validation (`src/auth/ActiveAuth.ts`)
The coverage report shows changes in `ActiveAuth.ts`. This suggests that the CLI may check on startup if the *currently* stored credential matches the enforced type. If a user was previously logged in via API Key, but the admin changes the setting to `oauth-personal`, the CLI will likely treat the user as "logged out" or prompt them to re-authenticate using the correct method.
