# What’s New in Gemini CLI: Extension Validation

**Release Date:** *[Insert Date]*
**Contributor:** @kevinjwang1
**PR Reference:** [#12186](https://github.com/google-gemini/gemini-cli/pull/12186)

## 1. Feature Summary

We have introduced a new command to the Gemini CLI toolkit: `extensions validate`.

This feature provides immediate feedback for developers building local extensions. By analyzing the `gemini-extension.json` manifest, the command acts as a linter, ensuring that naming conventions are met, referenced files actually exist, and versioning follows standard best practices. This proactive check helps prevent runtime errors and ensures high-quality extension metadata.

## 2. Background & Context

**The Problem:**
Previously, developing a Gemini CLI extension involved a manual process of ensuring the manifest file (`gemini-extension.json`) was accurate. Developers often encountered issues where:
*   Extensions failed to load due to illegal characters in the extension name.
*   Runtime errors occurred because a context file referenced in the JSON was missing or moved.
*   Version strings were inconsistent, leading to confusion during updates or package management.

**The Solution:**
Addressed in **PR #12186**, this change introduces a dedicated validation step. By shifting these checks left (before the extension is published or run), we significantly improve the developer experience. This ensures that only well-formed extensions make it into the ecosystem, reducing "it works on my machine" issues caused by simple configuration typos.

## 3. How-To Guide

Here is how to use the new validation command in your development workflow.

### Prerequisites
*   Ensure you have the latest version of the Gemini CLI installed.
*   Navigate to the root directory of your local extension (where your `gemini-extension.json` resides).

### Basic Usage

Run the following command in your terminal:

```bash
gemini extensions validate
```

### Scenario A: The Happy Path
If your extension is configured correctly, the CLI will confirm validity.

**Output:**
```text
✅ Extension metadata is valid.
```

### Scenario B: Catching Errors
If there are issues, the CLI will output specific errors or warnings.

**Example 1: Invalid Name**
*If your extension name contains spaces or special characters (e.g., "my extension!").*

**Output:**
```text
❌ Error: Extension name "my extension!" is invalid. 
   Only letters, numbers, and dashes are permitted.
```

**Example 2: Missing Context Files**
*If your JSON references `src/utils.py`, but the file was deleted.*

**Output:**
```text
❌ Error: Context file "src/utils.py" not found. 
   Please ensure all referenced files exist on the file system.
```

**Example 3: Semver Warnings**
*If your version is set to `v1.0` instead of `1.0.0`.*

**Output:**
```text
⚠️ Warning: Version "v1.0" does not adhere to standard semantic versioning (semver).
   Recommended format: MAJOR.MINOR.PATCH (e.g., 1.0.0).
```

## 4. Walkthrough / Technical Deep Dive

Under the hood, the `extensions validate` command performs a synchronous audit of the extension's structure. Here is the logic flow implemented in the PR:

1.  **Manifest Parsing:** The CLI locates and reads the `gemini-extension.json` file in the target directory.
2.  **Name Validation (Regex Check):**
    *   The command applies a strict regular expression against the `name` field.
    *   **Rule:** `^[a-zA-Z0-9-]+$`
    *   **Outcome:** If the check fails, a blocking **Error** is thrown. This safeguards the registry and CLI argument parsing from handling malformed names.
3.  **Context Integrity Check (File System I/O):**
    *   The parser iterates through the `context` array defined in the manifest.
    *   It verifies the existence of every file path relative to the manifest location.
    *   **Outcome:** If `fs.exists` returns false for any item, a blocking **Error** is raised. This prevents the extension from crashing mid-operation when it attempts to read a non-existent context file.
4.  **Semantic Versioning Check:**
    *   The `version` string is analyzed against standard SemVer patterns (Major.Minor.Patch).
    *   **Outcome:** If the format deviates, a **Warning** is issued. Unlike the previous checks, this does not block usage but advises the developer to align with community standards for better compatibility.
