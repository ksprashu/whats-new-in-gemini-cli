# 🚀 What’s New in Gemini CLI: Build Your Own IDE Plugin

**Version Update:** PR #8479
**Release Date:** *[Current Date]*
**Key Contributor:** @skeshive

## 1. Feature Summary
The Gemini CLI has officially opened its doors to ecosystem developers. We have published a comprehensive **IDE Plugin Specification**, allowing you to integrate Gemini’s AI capabilities directly into your editor of choice (VS Code, JetBrains, Neovim, Emacs, and more).

This update moves the Gemini CLI from being solely a terminal-based tool to a backend engine that can power rich, context-aware experiences and native in-editor diffing within any development environment.

## 2. Background & Context
**The Problem:**
Previously, using the Gemini CLI required context switching. Developers had to leave their IDE, go to the terminal, manually copy-paste code snippets for context, execute a prompt, and then copy the result back into the editor.

**The Solution:**
With PR #8479, we have updated the core bundle (`gemini.js`) and the associated sandbox security profiles to support programmatic interaction. The goal of this release (and the associated Issue #4800 context) is to standardize how external tools communicate with the Gemini CLI.

By publishing a formal spec, we solve two main friction points:
1.  **Context Awareness:** Plugins can now automatically feed open files or selected code blocks to the CLI without manual copy-pasting.
2.  **Structured Output:** The CLI can now return data in a format suitable for "native in-editor diffing," allowing IDEs to show accepted/rejected changes cleanly rather than just dumping text streams.

## 3. How-To Guide: Getting Started with the Spec

*Note: This guide assumes you are a tool builder or plugin maintainer looking to wrap the Gemini CLI.*

### Step 1: Update the CLI
Ensure you have the latest binary which includes the updated API logic and sandbox profiles.
```bash
npm install -g @google/gemini-cli@latest
# or update your specific binary bundle
```

### Step 2: Implement the Interface
While the full spec documentation is available in the repository `docs/`, the general workflow for a plugin builder is as follows:

1.  **Invoke the CLI in JSON/Machine Mode:**
    Your plugin should spawn the Gemini CLI process.
2.  **Pass Context:**
    Instead of relying on stdin prompts, pass file paths and line numbers as arguments.
    ```bash
    # Conceptual usage based on the spec
    gemini prompt "Refactor this function" --context ./src/main.js:10-25 --format=diff
    ```
3.  **Handle the Output:**
    The CLI will return a structured diff. Your plugin should parse this and use your IDE’s native `applyEdit` or diff view API to render the changes for the user.

## 4. Walkthrough / Technical Deep Dive

### The Binary Update (`bundle/gemini.js`)
The core logic in `gemini.js` (Size: 13.6 MB) has been updated to handle external invocation more robustly. The trivial size change (-2 B) suggests this was likely a refactor of the entry point to expose the plugin hooks or a compression optimization of the build artifact that exposes the new specification logic.

### Security and Sandboxing
A critical part of this update—and a requirement for safe IDE integration—is the update to the macOS sandbox profiles found in the PR:
*   `sandbox-macos-permissive-open.sb`
*   `sandbox-macos-restrictive-closed.sb`

**Why this matters:**
When an IDE plugin runs a CLI tool, it essentially executes code on the user's machine. The presence of these `.sb` (Sandbox) files indicates that the Gemini CLI now supports different security tiers when running as a plugin backend:
*   **Permissive/Open:** Likely used when the user grants the plugin full access to the project directory (required for analyzing large codebases).
*   **Restrictive/Closed:** Allows the CLI to process text input/output but prevents it from reading arbitrary files on the disk or making unauthorized network calls.

This architecture ensures that plugin developers can build tools that are secure by default, leveraging the CLI's internal sandboxing to protect user data.
