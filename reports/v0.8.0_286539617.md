# What’s New: Gemini CLI Extensions System

## 1. Feature Summary
The Gemini CLI has evolved from a standalone tool into a platform. With the new **Extensions Support**, developers can now build, share, and install custom commands directly into the Gemini CLI workflow.

Instead of waiting for the core team to add niche features, the community can now wrap complex prompt engineering workflows, API integrations, or system automation scripts into a single, installable command. This essentially transforms `gemini <prompt>` into `gemini <custom-tool>`.

## 2. Background & Context
**The Problem:**
As adoption of the Gemini CLI grew, the GitHub Issues tracker became flooded with requests for specific, niche workflows. Users wanted features like "automatic Git commit generation," "SQL query optimization," or "Jira ticket summarization."
*   **Issue:** Supporting every unique workflow in the core binary causes bloat and maintenance nightmares.
*   **Issue:** Users were hacking together bash aliases that were hard to share with their teams.

**The Solution:**
Based on the architectural discussions (PRs regarding modularity), the team decided to implement a decentralized extension model. This was driven by the philosophy that **the core tool should handle the model interaction (auth, streaming, formatting), while extensions handle the specific domain logic.**

This change decouples the core CLI release cycle from feature innovation, allowing the community to move faster than the maintainers.

## 3. How-To Guide

Here is how to consume and create extensions in the new version.

### Installing an Extension
Extensions are installed via Git repositories. To install a community extension (e.g., a hypothetical "PR Reviewer"):

```bash
# Install directly from a GitHub repository
gemini ext install user/gemini-pr-reviewer
```

Once installed, it becomes a first-class command:

```bash
# Use the extension
gemini pr-reviewer --branch main
```

### Managing Extensions
You can list and update your tools easily:

```bash
gemini ext list    # See what you have installed
gemini ext upgrade # Update all extensions
gemini ext remove  # Delete an extension
```

### Creating Your Own
To build an extension, you simply need an executable script and a manifest file.

1.  **Scaffold a new project:**
    ```bash
    gemini ext create my-new-tool
    ```
2.  **Edit the manifest (`extension.yml`):**
    ```yaml
    name: my-new-tool
    description: "Summarizes log files using Gemini"
    entry_point: script.sh
    ```
3.  **Write your logic (`script.sh`):**
    ```bash
    #!/bin/bash
    # You can call the core gemini binary from within the extension
    cat $1 | gemini "Analyze these logs and find the root cause error"
    ```

## 4. Walkthrough / Technical Deep Dive

Under the hood, the Extensions system relies on a lightweight dispatcher and a strict directory structure.

**1. The Extension Manager (`ext` command):**
When you run `gemini ext install <repo>`, the CLI clones the target repository into a strictly defined local data directory (usually `~/.config/gemini/extensions` or `XDG_DATA_HOME`). It looks for a manifest file (e.g., `extension.yml`) to validate the package.

**2. Dynamic Dispatch:**
When a user types a command that is *not* a core command (like `gemini my-tool`), the CLI:
1.  Checks the `extensions` directory for a folder matching the alias.
2.  Parses the manifest to find the `entry_point`.
3.  Spawns a child process to execute that script.
4.  Passes all subsequent arguments (`argv`) and environment variables (including Auth Tokens) to the child process.

**3. Composition:**
Crucially, extensions are **composable**. Because the `gemini` binary is in the user's PATH, extensions can recursively call `gemini` to perform inference. This allows developers to write the logic in Python, Node.js, Go, or Bash, while offloading the heavy lifting of API communication to the core CLI.
