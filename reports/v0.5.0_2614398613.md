# What’s New in Gemini CLI: Nested .gitignore Support

**Release:** *Latest*
**Contributor:** @gsquared94

## 1. Feature Summary
The Gemini CLI has been upgraded to support **nested `.gitignore` file handling**. Previously, the CLI primarily respected the `.gitignore` file located at the root of the execution directory. With this update, the CLI now traverses your project structure and respects ignore rules defined in subdirectories. This ensures that the context sent to the Gemini model is cleaner, strictly adheres to project configuration, and prevents the accidental inclusion of unnecessary or sensitive files located deep within complex project trees.

## 2. Background & Context
**The Problem:**
As highlighted in **Issue #3072**, developers working in monorepos or multi-module projects faced a significant friction point. When running the Gemini CLI from the project root, specific ignore rules defined inside sub-modules (e.g., `frontend/.gitignore` or `services/api/.gitignore`) were often overlooked.

This led to two major issues:
1.  **Context Pollution:** Large folders like `node_modules` or `__pycache__` located in subdirectories were inadvertently read and sent to the LLM if they weren't explicitly listed in the *root* `.gitignore`. This wasted token usage and confused the model.
2.  **Configuration Duplication:** Developers were forced to copy-paste subdirectory rules into the root `.gitignore` to ensure the CLI respected them, creating maintenance headaches.

**The Solution:**
Addressed in **PR #7645** by contributor **@gsquared94**, the file walker logic was refactored. The CLI now acknowledges the hierarchical nature of Git ignore patterns, ensuring that rules apply specifically to the directories they reside in, matching standard Git behavior.

## 3. How-To Guide
You don't need to change any configuration flags to enable this; it works out of the box. Here is a scenario to verify the behavior.

### Scenario: A Monorepo Structure
Imagine a project structure where you have a root directory and a nested `client` directory with its own dependencies.

**1. Setup the structure:**
```text
my-project/
├── .gitignore          (Root ignore)
├── server/
│   └── main.py
└── client/
    ├── .gitignore      (Nested ignore)
    ├── src/
    └── build/          (Should be ignored by client/.gitignore)
```

**2. Define the Ignore Rules:**
*   **Root `.gitignore`:** Contains standard system ignores (e.g., `.DS_Store`).
*   **Client `.gitignore`:** Specifically contains `build/`.

**3. Run Gemini CLI:**
Navigate to the root and run a command that consumes context (e.g., a codebase chat or context dump).
```bash
cd my-project
gemini chat "Analyze my project structure"
```

**4. Verification:**
The CLI will now read `server/main.py` and `client/src/`, but it will correctly **skip** `client/build/` because of the nested rule, even though `build/` was not explicitly listed in the root ignore file.

## 4. Walkthrough / Technical Deep Dive
In previous versions, the file discovery mechanism likely utilized a top-down approach that loaded exclusion patterns once at the start of the process.

With **PR #7645**, the file traversal logic has been updated to perform a **context-aware recursive walk**. Here is how it works under the hood:

1.  **Traversal:** As the CLI iterates through your directory tree, it checks every directory it enters for the presence of a `.gitignore` file.
2.  **Rule Stacking:** If a `.gitignore` is found, its rules are parsed and pushed onto a stack of active ignore patterns.
3.  **Path Matching:**
    *   When evaluating a file at `my-project/client/file.txt`, the CLI checks against the root rules.
    *   It then checks against the specific rules loaded from `my-project/client/.gitignore`.
4.  **Precedence:** The logic follows standard Git precedence. A rule in a nested directory applies only to that directory and its children.

This implementation reduces "token bloat" by ensuring that build artifacts, local environment files (`.env`), and vendor directories defined locally in sub-projects are automatically filtered out before the prompt is constructed.
