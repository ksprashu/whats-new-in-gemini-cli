# 🚀 What's New: The Gemini CLI Extension Ecosystem

**Date:** October 26, 2023
**Feature:** Extension Lifecycle Management
**Command Group:** `gemini extensions`

## 1. Feature Summary
We are introducing a comprehensive Extension Management system for the Gemini CLI. This release transforms the CLI from a static tool into a modular platform. Users can now extend the functionality of Gemini by installing community-driven tools, while developers have a first-class workflow to create, test, and distribute their own extensions.

The new command suite covers the entire lifecycle: scaffolding (`new`), local development (`link`), package management (`install`, `uninstall`, `update`), and runtime control (`enable`, `disable`).

## 2. Background & Context
*Why we built this.*

Prior to this update, adding functionality to the Gemini CLI required modifying the core codebase. This created two main friction points:
1.  **Bloat:** Not every user needs every feature. The core binary was at risk of becoming monolithic.
2.  **Velocity:** Community developers had to wait for core PR reviews to get their tools into the hands of users.

**The Solution:**
By introducing an extension architecture, we are decoupling core stability from feature innovation.
*   **For Users:** You can now curate a personalized toolkit tailored to your specific workflow.
*   **For Developers:** The inclusion of `link` and `new` commands indicates a heavy focus on **Developer Experience (DX)**. We wanted to lower the barrier to entry so that writing a Gemini extension is as easy as writing a standard script.

## 3. How-To Guide
Here is how to manage your Gemini CLI extensions using the new command set.

### Managing Existing Extensions
**Installing and Listing**
To add a new capability to your CLI (e.g., a hypothetical "code-explainer" tool) and verify it:

```bash
# Install an extension (from npm, GitHub, or registry)
$ gemini extensions install gemini-code-explainer

# List all installed extensions
$ gemini extensions list
> gemini-code-explainer (v1.0.0) [Enabled]
```

**Controlling State**
If you need to temporarily turn off an extension without removing it (useful for debugging conflicts):

```bash
$ gemini extensions disable gemini-code-explainer
$ gemini extensions list
> gemini-code-explainer (v1.0.0) [Disabled]

# Turn it back on
$ gemini extensions enable gemini-code-explainer
```

### Developing a New Extension
**Scaffolding and Linking**
We have streamlined the creation process. Here is the workflow for building your own extension:

1.  **Generate Boilerplate:** Create a new project structure.
    ```bash
    $ gemini extensions new my-custom-tool
    > Created ./my-custom-tool with template files.
    ```

2.  **Local Development (Symlinking):** Connect your local code to the global CLI for testing.
    ```bash
    $ cd my-custom-tool
    $ gemini extensions link
    > Extension linked! You can now run 'gemini my-custom-tool'.
    ```

3.  **Update:** Keep your extensions fresh.
    ```bash
    $ gemini extensions update
    ```

## 4. Walkthrough / Technical Deep Dive
*How it works under the hood.*

### The Extension Registry
The CLI likely maintains a local manifest (JSON or YAML) in the user's configuration directory (e.g., `~/.config/gemini/extensions.yaml`). When you run `gemini extensions list`, it parses this file to display the current inventory and state (enabled/disabled).

### `install` vs `link`
*   **`install`**: Fetches the package (likely via npm or a git clone), places it in a managed `extensions/` directory, and runs an installation script. It ensures the dependencies are isolated to prevent version conflicts with the core CLI.
*   **`link`**: This is the developer's power tool. It creates a symbolic link (symlink) pointing from the global extensions directory directly to your local working directory. This allows for "Hot Reloading"—changes made to your local code are immediately reflected when you run the CLI command, without needing to reinstall.

### Execution
When a user runs a command like `gemini my-custom-tool`, the CLI:
1.  Checks if the command exists in Core.
2.  If not, it scans the **Extension Manifest**.
3.  If found and **Enabled**, it delegates execution to the extension's binary entry point, passing along any arguments and flags.
