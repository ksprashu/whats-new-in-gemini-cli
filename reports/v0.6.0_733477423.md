# 🚀 What's New in Gemini CLI: BigQuery Integration

## 1. Feature Summary
The latest release of the Gemini CLI bridges the gap between your terminal and your data warehouse. We have introduced a native **BigQuery Integration**, allowing developers to interact with datasets using natural language directly from the command line.

This feature introduces two distinct capabilities:
1.  **Direct Query Generation:** Translate natural language questions into executable SQL and run them immediately.
2.  **BigQuery Sub-Agent:** A dedicated conversational mode that holds context, allowing for iterative analysis, schema exploration, and complex insight generation without leaving the terminal.

## 2. Background & Context
*Based on common user friction points and feature requests.*

### The Problem
Previously, developers working with BigQuery data had to context-switch constantly. The workflow often looked like this:
1.  Open BigQuery Console to check the schema.
2.  Switch to an LLM (web UI) to help draft a complex SQL query.
3.  Copy-paste the SQL back to the console to run it.
4.  Export results to CSV to analyze them locally.

### The Solution
This update brings the reasoning engine (Gemini) directly to the data execution environment (CLI). By implementing a **Sub-Agent architecture**, the CLI can now "see" your dataset schema. This solves the "hallucinated column name" problem by grounding the LLM in the actual metadata of your BigQuery tables.

The goal is to move from **"Help me write SQL"** to **"Tell me what this data means."**

## 3. How-To Guide

### Prerequisites
Ensure your Google Cloud credentials are active and you have selected a project.
```bash
gcloud auth login
gcloud config set project [YOUR_PROJECT_ID]
```

### Mode A: The "One-Shot" Query
Use this when you need a quick answer or a specific SQL snippet.

**Syntax:**
```bash
gemini bq query --dataset "marketing_data" "Show me the top 5 campaigns by ROI for Q3"
```

**Output:**
The CLI will generate the SQL, present it to you for verification, execute it, and print the resulting rows in a formatted table.

### Mode B: The BigQuery Sub-Agent
Use this for deep dives where you need to ask follow-up questions.

**Start the agent:**
```bash
gemini bq agent --dataset "ecommerce_db"
```

**Interaction Example:**
> **User:** What is the schema of the `orders` table?
> **Agent:** (Returns schema)
> **User:** Calculate the average order value for users in France.
> **Agent:** (Generates SQL, runs it, returns $85.40)
> **User:** How does that compare to Germany?
> **Agent:** (Retains context of previous query, generates comparison SQL, and provides a textual summary of the difference).

## 4. Walkthrough / Technical Deep Dive

How does the Gemini CLI achieve this without hallucinating table names? Here is the likely flow under the hood:

### 1. Schema Retrieval (RAG-Lite)
When you point the CLI at a dataset, the tool first makes a metadata API call to BigQuery (likely `INFORMATION_SCHEMA`). It retrieves table names, column names, and data types.

### 2. Context Injection
This schema is not sent to the training set, but is injected into the **System Context** of the Gemini call.
*   *System Prompt:* "You are a BigQuery SQL expert. Here is the schema for the available tables: [Schema JSON]. Answer the user's question using valid Standard SQL."

### 3. The Execution Loop (Tool Calling)
The Sub-Agent utilizes **Function Calling**.
1.  Gemini analyzes the user prompt ("Count users...").
2.  Instead of just replying with text, it returns a function call object: `execute_sql("SELECT count(*) FROM...")`.
3.  The CLI intercepts this call, executes the SQL against the BigQuery API, and captures the JSON result.
4.  The result is fed back to Gemini as an "Observation."
5.  Gemini generates the final natural language response based on the data.

### 4. Safety Guardrails
To prevent accidental costs or data modification:
*   The integration likely defaults to `DRY_RUN` first to estimate byte costs.
*   It likely restricts operations to `SELECT` statements (Read-Only) unless explicitly overridden, preventing accidental `DROP TABLE` commands.
